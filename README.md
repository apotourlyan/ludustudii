Ludus Studii ("The Study Game") — Turn complex study material into structured, gamified learning loops.

## Backend

A single Go binary serves the JSON API under `/api`, the embedded React client
app, root-level operational probes, and (optionally) an interactive API
reference under `/docs`.

### Stack

| Area | Choice |
| --- | --- |
| Language | Go 1.27 |
| HTTP | `net/http` + `http.ServeMux` |
| Database | PostgreSQL 18 via `database/sql` + [pgx](https://github.com/jackc/pgx) (no ORM, hand-written SQL) |
| Migrations | [goose](https://github.com/pressly/goose), SQL files embedded in the binary |
| IDs | UUIDv7 generated by PostgreSQL (`uuidv7()`), so ID order is creation order |
| Logging | `log/slog`, JSON or text, with per-request IDs |
| API contract | OpenAPI 3.0 in `backend/apispec`, validated with [kin-openapi](https://github.com/getkin/kin-openapi) |
| API reference | [Scalar](https://github.com/scalar/scalar), self-hosted and embedded behind a build tag |
| Live reload | [Air](https://github.com/air-verse/air) |

### Layout

```
backend/
├── cmd/
│   ├── server/api/        # main: the HTTP server
│   └── tools/bundlespec/  # bundles the OpenAPI spec into one JSON file
├── apispec/               # OpenAPI spec (openapi.yml, paths/, components/), embedded
├── migrations/            # goose SQL migrations, embedded (see goose.md)
├── tools/                 # separate module for pinned development tools
└── internal/
    ├── app/               # composition root: config, logger, DB; composes the surfaces (handler.go)
    │   ├── api/           # API surface: every service under /api
    │   ├── router/        # shared HTTP front: root mux, middleware chain, central error handler
    │   └── server/        # process lifecycle: serve, drain, graceful shutdown
    ├── infra/             # env, health (probes), logging, rdb (Postgres), spa (client app), apidocs
    ├── kit/               # helpers independent of app and infra: erresp, validator, sanitizer, staticfile, httpkit
    ├── services/
    │   └── lcards/        # learning cards: one subpackage per endpoint
    │       ├── domain/    # shared rules, limits and constants
    │       ├── create/    # handler.go + store.go
    │       ├── get/
    │       ├── list/
    │       ├── update/
    │       └── remove/
    └── testkit/           # test-only helpers: isolated DBs, HTTP client, OpenAPI checks
```

Each endpoint is a vertical slice with its own `Handler` and `Store`. A handler
binds, sanitizes and validates the request, then calls its store through a
small interface. Each store query lives in its own `.sql` file beside `store.go`,
with a header comment listing its placeholders, and is embedded with `//go:embed`.
Stores contain no inline SQL strings. Package boundaries are enforced by `depguard`:

- `kit` must not import `infra`, `services` or `app`.
- `services` must not import `infra` or `app`.
- `app/router` and `app/server` must not import the rest of `app`, `services`,
  any surface (`health`, `spa`, `apidocs`) or `rdb`, including from their tests.
- The surfaces (`app/api`, `health`, `spa`, `apidocs`) must not import the rest
  of `app`, each other, `env` or `rdb`, including from their tests.
- `testkit` may only be imported from test files.

#### Surfaces and startup

The HTTP server is composed of surfaces. Each is built on its own, owns its
patterns on one root `http.ServeMux` and needs only its own dependencies:

| Surface | Patterns | Built by | Needs |
| --- | --- | --- | --- |
| Probes | `/livez`, `/readyz` | `health.NewProbes` | readiness state |
| API | `/api`, `/api/` | `api.New` (`internal/app/api`) | database |
| API reference | `GET /docs`, `GET /docs/{$}`, `GET /docs/openapi.json`, `GET /docs/scalar.js` | `apidocs.NewHandler`, only when enabled | embedded files |
| Client app | `/` (catch-all) | `spa.NewHandler` | embedded files |

A surface implements `router.Surface` (`Mount(*http.ServeMux)`). `router.New`
mounts the surfaces it is given and wraps the root mux once with the
middleware chain; it knows no surface. Surfaces that platforms poll also
implement `router.QuietSurface`, so their request summaries log at debug.
Every surface reports errors to the same `router.ErrorHandler`.

`internal/app` is the composition root and the only package that knows every
surface. `app.Run` loads the configuration, the client app, the optional
reference and the database. `newHandler` (`internal/app/handler.go`) builds the
surfaces and mounts them, and `server.Run` owns the process lifecycle:
serving, draining and graceful shutdown. Tests compose only the surfaces they
need. Service API tests mount the API surface alone, for example. A future
binary that serves a subset of the surfaces needs a new composition root, not
changes to the surfaces ([ADR 0001](docs/adr/0001-single-binary-services-as-packages.md)).

#### Routing

The root mux sends `/api` and `/api/` to an `httpkit.API`, which has its own
mux for the API routes. Both muxes serve requests themselves, so they set
`Request.Pattern` and wildcard path values (`r.PathValue("id")`).

- **API endpoints** register with `api.HandleFunc`, one call per method and
  path, in each service's `routes.go`. Each service's `RegisterRoutes` is
  called from `api.New`:

  ```go
  api.HandleFunc("GET "+domain.CardsPath+"/{id}", g.Handle)
  api.HandleFunc("PUT "+domain.CardsPath+"/{id}", u.Handle)
  api.HandleFunc("DELETE "+domain.CardsPath+"/{id}", d.Handle)
  ```

  Patterns always include the method, and GET also serves HEAD. Literal
  segments such as `/api/lcards/due` can sit next to `/api/lcards/{id}`.
- **Unknown API paths and methods** are decided by the API mux. `httpkit.API`
  runs the mux's own 404 or 405 handler against a probe and reports
  `not_found`, or `method_not_allowed` with the mux's `Allow` header (methods
  sorted alphabetically, across every pattern that matches the path). An `/api`
  path never reaches the SPA.
- **Probes** reserve `/livez` and `/readyz` outside the API and the SPA. GET
  also serves HEAD; other methods receive JSON `405 method_not_allowed` with
  `Allow: GET, HEAD`.
- **`/docs`** routes are `GET` patterns, registered only when the reference is
  enabled; other methods fall through to the SPA.
- **The SPA** is the method-less `/` catch-all and answers non-GET/HEAD
  methods with a plain-text `405`. It cannot be `GET /`, which conflicts with
  `/api/`.
- Paths with `//`, `.` or `..` segments get the mux's `307` redirect to the
  cleaned path.

The request log's `route` is the matched mux pattern, for example
`GET /api/lcards/{id}`, `/api/` for an unknown API path or method (`/api` for
the bare path), or `/` for the SPA. It is empty when middleware rejects a request
before routing, such as a `413` for a declared body over the limit.

Handlers return failures to the app's central error handler, which writes the
shared JSON error shape. `httpkit` request errors retain their causes and named
responses; `kit.ErrNotFound` maps to 404.
Status errors carry their own status and response body and are logged at debug
level. All other errors are logged at error level and returned as a generic 500.
Handler function fields remain the seams for isolating binding and validation
in unit tests.

Production environment variables are read only in `internal/infra/env`; the
`testkit` harness reads `DB_TEST_CONNECTION` directly. Application logging goes
through `log/slog` (`fmt.Print*` and `log.*` are forbidden by the linter).

### API

| Method | Path | Description | Success |
| --- | --- | --- | --- |
| `GET` | `/api/lcards` | List cards, newest first, keyset-paginated | `200` |
| `POST` | `/api/lcards` | Create a card | `201` + `Location` header |
| `GET` | `/api/lcards/{id}` | Get a card | `200` |
| `PUT` | `/api/lcards/{id}` | Replace a card's title and description | `204` |
| `DELETE` | `/api/lcards/{id}` | Delete a card | `204` |

`HEAD` is supported wherever `GET` is. The OpenAPI spec in `backend/apispec`
is the source of truth; the notes below summarize it.

- **Requests** with a body must use `Content-Type: application/json` (otherwise
  `415`). Bodies are limited to 1 MiB (`413`). Unknown JSON fields are rejected
  with `400 bind_error`.
- **Cards** have `id`, `title`, `description`, `created_at` and
  `updated_at`, in single-card responses and in list items. The timestamps
  are the database's clock, as RFC 3339 in UTC (`2026-11-18T09:30:00.123456Z`):
  `updated_at` equals `created_at` until the first update and changes with
  every one ([ADR 0040](docs/adr/0040-row-timestamps-in-the-api.md)). They
  are read-only: request bodies take only `title` and `description`, and a
  body with either timestamp gets `400 bind_error`, like any unknown field.
- **Input** strings are normalized to Unicode NFC and trimmed before
  validation. Title is 1–200 and description 1–2000 code points; the database
  enforces the same limits with `CHECK` constraints.
- **IDs** are hyphenated UUIDv7, accepted in any letter case.
- **Concurrency**: the last write wins
  ([ADR 0039](docs/adr/0039-last-write-wins-for-user-edited-resources.md)).
  PUT replaces a card and DELETE removes it, whatever the client read before;
  cards have no version, and there are no conditional requests. Requests check
  path ID, binding, sanitization, validation, then storage.
- **Pagination**: `limit` (1–100, default 20) and `cursor` (the previous
  page's `next_cursor`, an opaque token to pass unchanged). `next_cursor` is
  `null` on the last page. Invalid tokens report `invalid_cursor`. Malformed
  or overflowing limits return `validation_error` with `invalid_integer`; integer limits outside 1–100
  return `validation_error` with `out_of_range`.
- **Request IDs**: every response carries `X-Request-Id`. The first client-supplied
  value is reused only if it contains 1–128 ASCII letters, digits, `.`, `_` or
  `-`. Missing, empty or invalid values are replaced with a random base32 ID,
  without rejecting the request. The selected ID is attached to every log
  record for that request.
- **Errors** share one JSON shape. Errors from shared middleware, such as
  oversized bodies and recovered panics, use it on every path, client-app
  paths included; the client app's own errors are plain text. `errors` is
  present only for validation failures in body fields, path parameters or
  query parameters:

  ```json
  {
    "code": "validation_error",
    "errors": [{ "field": "title", "code": "max_length" }]
  }
  ```

  | Code | Status | Meaning |
  | --- | --- | --- |
  | `bind_error` | 400 | Body could not be decoded |
  | `validation_error` | 400 | A body field, path parameter or query parameter failed validation |
  | `not_found` | 404 | Unknown card or unknown `/api` path |
  | `method_not_allowed` | 405 | Unsupported method, with an `Allow` header |
  | `payload_too_large` | 413 | Body over 1 MiB |
  | `unsupported_media_type` | 415 | Body is not `application/json` |
  | `unexpected_error` | 500 | Server-side failure; details are only logged |

  Field error codes: `required`, `max_length`, `untrimmed`, `not_normalized`,
  `invalid_integer`, `out_of_range`, `invalid_uuid7` (invalid path ID),
  `invalid_cursor` (invalid pagination token).

### Probes

`internal/infra/health` owns the probes surface (`health.Probes`) and the
shared `health.State`. The composition root mounts the probes and passes the
same state's `MarkStopping` to `server.Run` as its `OnDrain` hook, which runs
when shutdown begins.

`GET /livez` (and HEAD) returns 200 whenever the process can answer HTTP. It
checks no dependencies, including the database. Use it for liveness checks.
`GET /readyz` (and HEAD) returns 200 only when a database ping succeeds within
one second and the instance is not shutting down; otherwise it returns 503.
Use readiness to decide whether to send traffic to an instance.

Both paths live outside `/api` and require no authentication. Probe handlers
send `Cache-Control: no-store` and `X-Request-Id`. GET bodies are
`{"status":"ok"}` or `{"status":"unavailable"}`; HEAD sends no body.
Unsupported methods receive 405 with the shared JSON error body
`{"code":"method_not_allowed"}` and `Allow: GET, HEAD`.

The global 1 MiB body limit also applies to both paths. Oversized declared
bodies return JSON `413 payload_too_large` before the probe handler runs;
HEAD sends no body.

On SIGINT or SIGTERM, readiness becomes unavailable immediately. HTTP keeps
serving during `APP_SHUTDOWN_DRAIN_DELAY`, allowing load balancers to remove
the instance, then graceful shutdown begins with `APP_SHUTDOWN_TIMEOUT`.
The drain delay defaults to `0s`; deployments set it to match their routing
propagation time. A second signal terminates immediately during draining or
shutdown.

For a Docker Compose image containing `curl`, a readiness healthcheck can be:

```yaml
services:
  app:
    environment:
      APP_PORT: "8080"
      APP_SHUTDOWN_DRAIN_DELAY: "5s"
    stop_grace_period: 25s # Allow the drain delay plus the shutdown timeout.
    healthcheck:
      test: ["CMD", "curl", "--fail", "--silent", "--max-time", "2", "http://localhost:8080/readyz"]
      interval: 5s
      timeout: 3s
      retries: 3
```

### Configuration

The server reads its configuration from environment variables at startup and
reports every missing or invalid variable at once. The devcontainer sets the
required ones.

| Variable | Default | Description |
| --- | --- | --- |
| `DB_CONNECTION` | **required** | PostgreSQL URL (`postgres://` or `postgresql://`) |
| `APP_PORT` | **required** | Decimal HTTP port, 1–65535 |
| `DB_MAX_OPEN_CONNS` | `10` | Connection pool size |
| `DB_MAX_IDLE_CONNS` | `5` | Idle connections kept in the pool |
| `DB_CONN_MAX_LIFETIME` | `30m` | Maximum connection lifetime |
| `DB_CONN_MAX_IDLE_TIME` | `10m` | Maximum connection idle time |
| `APP_READ_TIMEOUT` | `5s` | HTTP read timeout |
| `APP_WRITE_TIMEOUT` | `10s` | HTTP write timeout |
| `APP_IDLE_TIMEOUT` | `90s` | HTTP keep-alive idle timeout |
| `APP_SHUTDOWN_TIMEOUT` | `15s` | Grace period for in-flight requests after draining on SIGINT/SIGTERM |
| `APP_SHUTDOWN_DRAIN_DELAY` | `0s` | Wait after marking the instance unready, before graceful shutdown |
| `APP_API_DOCS` | `false` | Serve the API reference at `/docs` (`make dev` sets `true`) |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn` or `error` |
| `LOG_FORMAT` | `json` | `json` or `text` |
| `DB_TEST_CONNECTION` | — | Test-only: server and role used by integration tests (needs `CREATEDB`) |

Durations use Go's `time.ParseDuration` syntax. The connection string is
logged at startup with its password redacted.

## Client app

A React app in `frontend/`, built with Vite and embedded in the binary. It
reads and changes server data through TanStack Query
([ADR 0030](docs/adr/0030-server-state-owned-by-tanstack-query.md)) and is
sliced into modules by user activity
([ADR 0035](docs/adr/0035-client-app-modules-by-user-activity.md)), whose
pages read route data and whose components take props
([ADR 0036](docs/adr/0036-pages-read-route-data-components-take-props.md)).
A component with behavior is a state hook and a view, with its rules in
the module's `model/`
([ADR 0042](docs/adr/0042-component-structure-logic-state-and-view.md),
[Component structure](#component-structure)).

### Structure

```
frontend/
├── src/
│   ├── main.tsx            # bootstrap: starts the mock mode's fake backend, if any, then renders the app
│   ├── app/                # the shell: query client, router, root layout and navigation, toaster, navigation progress, pending, error and not-found pages
│   ├── routes/             # TanStack Router's file routes: path, params, a loader calling the page's load function, and the page
│   ├── routeTree.gen.ts    # generated from routes/ by the router's Vite plugin
│   ├── modules/            # one folder per user activity
│   │   └── library/        # managing content: learning cards
│   │       ├── index.ts    # the module's public surface: its pages, their load functions and search params validators
│   │       ├── pages/      # one component per route (<page>.tsx), and beside it the load function that fills what it reads (<page>.load.ts) and, for a page with display state, its search params validator (<page>.search.ts)
│   │       ├── components/ # the pages' parts, which take data as props; one with behavior as <name>.state.ts, <name>.view.tsx and <name>.tsx; private to the module
│   │       └── model/      # plain TypeScript logic: rules, checks, wording, such as the card fields and messages
│   ├── shared/             # used by every module, knows none of them; only these three folders
│   │   ├── lib/            # helpers, hooks and rules, such as the wording for the failures every module shares and notifyError
│   │   ├── components/     # the app's own components every module can use, such as the recent-change mark, ConfirmDeleteButton, how a module deletes something after a confirmation, CollectionViewSwitch, which switches a collection between a list and a grid, and VirtualItemList, which renders only the items near the window
│   │   └── ui/             # shadcn's components (see UI components)
│   ├── api/                # one folder per backend service, its fake in <service>/fake/ (ADR 0030, 0032)
│   ├── mock/               # the mock mode's start-up and scenarios
│   ├── test/               # what the unit and component tests share: the fake backend in the test page, render helpers
│   └── styles/             # Tailwind theme and the ejected shadcn CSS
├── tests/                  # Playwright's browser tests: mock/, e2e/ and shared support/
└── tools/                  # the API type generator, with its own pinned TypeScript 5
```

- **`src/app/`** is the only code that may combine several modules, such as
  a navigation or, later, a dashboard built from what each module exports.
- **`src/routes/`** stays thin: a route file declares its path and params,
  checks its search params with its page's validator, if the page has
  display state (`validateSearch: validateLearningCardsPageSearch`), calls
  its page's load function in its loader
  (`loader: ({ context: { queryClient } }) =>
  loadLearningCardsPage(queryClient)`), and renders a page from a module's
  index. Pages take route
  params as props. `frontend/package.json` declares only CSS as having side
  effects (`sideEffects`), so the build drops the index's other exports from
  each route's chunk, and every route still gets a chunk of its own. That
  holds because the router keeps loaders in the initial bundle and a load
  function lives in its own file that imports no UI, so a loader never pulls
  its page in.
- **A module** has a fixed shape: `index.ts`, `pages/` and `components/`, and
  `model/` for plain TypeScript logic or `widgets/` once it needs one. Today
  there is one, `library`; `practice`, `planning`, `dashboard` and
  `progress` follow as they are built. URLs start with the module
  ([The library](#the-library) lists its URLs), and the route files are
  grouped the same way, in `src/routes/library/`. `/` and `/library`
  redirect to `/library/cards` until the dashboard exists.
- **Wording:** the API layer has none
  ([ADR 0031](docs/adr/0031-generated-api-types-and-typed-fetch-client.md)).
  `errorMessage` in `src/shared/lib/error-message.ts` words the failures every
  module shares: the network, server errors and anything unexpected. A module
  words what is about its own resources, such as a missing or changed card,
  in a `FailureWording` it passes to `errorMessage`
  (`modules/library/model/learning-card-error-message.ts`).

#### The library

| URL | Page | Shows |
| --- | --- | --- |
| `/library/cards?view=list` | `LearningCardsPage` | The cards' titles, newest first, one row each, each with Open, Edit and Delete, and a mark on a card created or updated in the last 5 minutes |
| `/library/cards?view=grid` | `LearningCardsPage` | The same, as a grid of cards of one size |
| `/library/cards/new` | `LearningCardNewPage` | The form for a new card, with its preview |
| `/library/cards/$cardId` | `LearningCardPage` | One card, its title the page's `<h1>`, with Edit and Delete |
| `/library/cards/$cardId/edit` | `LearningCardEditPage` | The form for that card, its preview where `LearningCardPage` shows the card, so opening the editor doesn't move it |

The overview, `/library/cards`, shows the cards as a list or a grid,
switched by the two icon buttons next to its "Add card" link ("List view"
and "Grid view"). The view is in the URL: `view=grid` is the grid, and
anything else, or nothing, the list. The router writes the default into
the URL, so links to the overview, and the redirects from `/` and
`/library`, end on `?view=list`. A list row shows a title on one line and
a grid card up to three, each cut with an ellipsis; the grid has 4 cards
per row from `lg`, 3 from `md`, 2 from `sm` and 1 below. Both views render
only the items near the window, with TanStack Virtual's window virtualizer:
every row and card has a fixed height, so nothing is measured, and each
rendered item carries `aria-posinset` and `aria-setsize`, so assistive
technology knows its place among all the cards. The page scrolls, and Back
returns to where it was scrolled: the router's scroll restoration
(`scrollRestoration` in `src/app/router.ts`) restores the window, and the
page reads the position it is about to restore with
`useElementScrollRestoration` and passes it to the view as its initial
offset, so the first render already shows the items there. The overview
loads the first page of cards, 100, the most the API serves at once.

The overview marks the cards created or updated in the last 5 minutes, so
cards just added or edited, here or in another tab or device, are found at
a glance. A card created in that window is new, a blue sparkle; otherwise
one updated in it is updated, an amber clockwise clock; a card created and
then edited within it stays new. The window is `RECENT_CHANGE_WINDOW_MS`
in `src/shared/lib/recent-change.ts`, and the times are the API's
`created_at` and `updated_at`, compared with the device's clock
([ADR 0040](docs/adr/0040-row-timestamps-in-the-api.md)). The rule takes
any `created_at` and `updated_at`, and the mark is
`src/shared/components/recent-change-mark.tsx`, so another module can mark
its own resources the same way. The page reads
the time once with `useNow` (`src/shared/lib/use-now.ts`), which renders
it again every minute, so a mark goes within a minute of its window's end
without a reload. In the list, the mark leads the title, and every row
keeps its space, so the titles line up; in the grid, it sits in the
card's top right corner, and every card's title stops short of it, so
titles wrap the same with or without one. The icon has no frame and
isn't interactive, so it doesn't read as a button; it is hidden from
assistive technology, and hidden text, "New" or "Updated", is read before
the title. Its colors are the
theme's `--recent-new` and `--recent-updated` (`src/styles/global.css`),
each at least 3:1 against a card in both themes. The marks are only on
the overview, which keeps its newest-first order.

Both card URLs show `LearningCardNotFoundPage` for an ID that names no card.
Creating a card and saving an edit end on the card's page; Cancel goes to
the card's page from its editor, and to the list from the new card's form.
Deleting a card on its page ends on the list; deleting one in the list
stays there.

A card's Markdown renders through two components in
`components/learning-card-markdown.tsx`. `LearningCardTitleMarkdown`
renders a title as inline Markdown only (bold, italic, code and links);
other syntax is unwrapped to its text, so `# Photosynthesis` reads
"Photosynthesis" and a title fits in any heading or line.
`LearningCardDescriptionMarkdown` renders a description with its headings
one level down, `#` as `<h2>` through `#####` and `######` as `<h6>`, so a
page's own `<h1>` stays its only one.

#### Pages, components and widgets

[ADR 0036](docs/adr/0036-pages-read-route-data-components-take-props.md)
decides what each kind of file in a module may do:

| Folder | Reads queries | Gets its data from | Handles loading and failure |
| --- | --- | --- | --- |
| `pages/` | with `useSuspenseQuery`, only what its load function fills | the cache, filled before it renders | no: the route's pending and error components do |
| `components/` | never | props | no |
| `widgets/` | its own | its own fetch | yes, itself |

- **A page** (`pages/<page>.tsx`) exports only its component, and its load
  function lives beside it in `pages/<page>.load.ts`, such as
  `loadLearningCardEditPage(queryClient, cardId)` in
  `learning-card-edit-page.load.ts`. The load function fills every query
  the page reads and nothing else, returns no data, and turns a missing
  resource into the router's `notFound()`. A page that reads exactly what
  another reads may call that page's load function from its own
  (`loadLearningCardEditPage` calls `loadLearningCardPage`). A load file
  imports only the API layer and the router, never UI, since it is in the
  initial bundle. The page owns the
  screen: its `<h1>`, its width and placement, and what follows a
  successful action, such as going to the card's page. The root layout
  provides the `<main>` landmark around every page.
- **History:** after an action that uses up the current page (a create)
  or removes what it shows (a delete), a page navigates with
  `replace: true`, so Back doesn't return to an empty form or to a missing
  card. Any other navigation pushes.
- **Display state**, such as the overview's chosen view, lives in the
  URL's search params, so a reload, Back or a shared link keeps it. The
  route checks them with `validateSearch`, which calls the page's
  validator in `pages/<page>.search.ts` (`validateLearningCardsPageSearch`), and
  turns anything invalid or missing into the default (for a collection's
  view, `parseCollectionView` in `src/shared/lib/collection-view.ts`). The
  page reads them with `useSearch`, and changing them navigates with
  `replace: true`, so Back leaves the page instead of stepping through
  each change. Changing them doesn't reload the page's data either: the
  router runs a page's loader again for a navigation that only changes its
  search params (a "stay") only when it goes to the very same URL, so
  switching views never waits for a refetch or fails on one
  (`tests/mock/views.spec.ts` checks it). Entering the page runs the loader as on every route
  ([ADR 0030](docs/adr/0030-server-state-owned-by-tanstack-query.md)).
- **A component** takes data as props and owns only UI state. It may call
  a mutation hook for the interaction it owns (a delete button and its
  dialog), renders links instead of navigating, reports outcomes through
  callbacks (`onSaved`), and leaves its page width and outer margins to its
  parent.
- **Modes of one thing**, such as viewing, previewing and editing a card,
  share a frame component with slots, and each mode is its own component
  that fills them: `LearningCardFrame` lays out a card's strip and its title
  and description sections, and `LearningCardDisplay`, `LearningCardPreview`
  and `LearningCardForm` fill it. No mode prop that switches the logic.
- **A widget** is data the page shouldn't wait for: it owns its query and
  shows its own loading and failure, behind its own Suspense and error
  boundary, or inline with `useQuery` where suspending would be wrong. A
  page renders widgets, and `src/app/` composes them across modules through
  each module's index. The `widgets/` folder is created with the first
  widget; none exists yet.

### Forms

[ADR 0038](docs/adr/0038-form-validation-errors.md) decides how a form
shows what is wrong with its fields. The card form is the reference: its
save workflow in `modules/library/components/learning-card-form.state.ts`,
its markup in `learning-card-form.view.tsx`, and its fields as components
of the card form's setup, `learning-card-form-hook.ts`
([Component structure](#component-structure)).

- **Validators return the API's field codes**, not text
  (`model/learning-card-fields.ts`: `required`, `max_length`). The limits
  live in that file, next to the checks.
- **One wording function per module** turns a field and a code into the
  message, or undefined for a pair it has no wording for
  (`model/learning-card-field-message.ts`). The form renders its field's codes
  through it, so a client error and the API's read the same.
- **The API's field errors go on their fields.** `placeFieldErrors` in
  `src/shared/lib/field-errors.ts` splits a failed save's field errors into the
  codes per form field that the wording can place and whether anything was
  left over; a form that names a field differently from the API passes a
  name map. `learningCardSaveFailure` in `model/learning-card-form.ts`
  turns that into what the card form does: the codes per field, the toast,
  and what to log. The form puts the codes in the field's `onServer` error,
  so `canSubmit`, the invalid look and the error rendering are TanStack
  Form's own. A field's server error clears when its value changes, not when it
  loses focus (`keepServerErrorsOnBlur` in
  `src/shared/lib/keep-server-errors-on-blur.ts`, the form's
  `validationLogic`).
- **A form reports a failed submit with `useFormFailure(form, fields,
  formRef)`** from `src/shared/lib/use-form-failure.ts`. The module's `model/`
  turns the error into a `FormFailure` (the codes per field, the toast and
  what to log; `learningCardSaveFailure` for the card form), and
  `report(failure)` applies it: the codes go in each field's `onServer`
  error, the toast through `useErrorToast` ([Feedback](#feedback)), the log
  to `console.error`, and the focus to the first invalid field.
  `clear()` closes the toast when the user submits again, and
  `focusFirstInvalid()` is the form's `onSubmitInvalid`.
- **After a failed submit the first invalid field, in the form's order,
  gets the focus**, whoever rejected it.
- **Everything that isn't about a field is a toast**
  ([Feedback](#feedback)): an error the form can't place (an unknown field
  or code, which is also logged to the console with its request ID), a
  `bind_error`, other HTTP failures and network failures. The form shows
  nothing of them itself.

### Feedback

[ADR 0041](docs/adr/0041-feedback-toasts-page-states-and-navigation-progress.md)
decides how the client app reports outcomes and waits.

- **A failure that isn't about a field is a toast**: a save no field can
  show, a delete, a network failure. The call site words it with its
  module's wording and calls `notifyError(message)` from
  `src/shared/lib/notify.ts`; the API layer reports nothing. An error toast
  stays until dismissed (its Dismiss button, or F6, Tab and Escape) or
  until its call site tries the action again (`notifyError` returns a
  function that closes it). For an action that can be retried, such as a
  save or a delete, `useErrorToast()` from `src/shared/lib/use-error-toast.ts`
  keeps that function: `show(message)` replaces the toast of the last
  failure, and `clear()` closes it when the user tries again. It is announced at once and doesn't stack:
  each message has one toast, and a repeat replaces it, in front, and is
  announced again. The
  toasts are Base UI's, through shadcn's `toast`, mounted once in
  `src/app/app.tsx`; nothing else uses them ([Boundaries](#boundaries)).
  They sit at the bottom left, clear of every page's controls at 1280×720
  (`tests/mock/toast-position.spec.ts`), and across the bottom below `sm`.
- **A confirmation dialog closes when its request settles**; a failure
  becomes a toast, which outlives the dialog and its row.
- **No success toasts while the result is visible**: a save opens the
  card's page, and a delete removes the card from view.
- **A decision is an alert in the page, never a toast**: it stays until the
  user resolves it. None exists yet; the first one chooses its component.
- **A navigation shows progress**: `NavigationProgress`
  (`src/app/navigation-progress.tsx`), a thin bar at the top of the
  viewport while the router loads, after `NAVIGATION_PROGRESS_DELAY_MS`
  (150 ms), still under reduced motion, and hidden from assistive
  technology, since the pending page announces a long wait. No skeletons.
- **Failure pages have one `<h1>`**: `RouteError` ("This page couldn't
  load", the reason, "Try again") and `NotFoundPage` ("Page not found", a
  link to the library) are the router's defaults; a missing card has
  `LearningCardNotFoundPage`. A failed background refetch stays silent (ADR
  0030).

### Boundaries

`make frontend-lint` enforces them with `no-restricted-imports` overrides in
`frontend/oxlint.config.ts` ([Linting](#linting)):

- Modules don't import each other, `src/app/` or `src/routes/`. They connect
  through URLs, and `src/app/` combines them.
- From outside a module, only its index is imported (`@/modules/library`).
  Inside, imports are relative and stay inside the module: no `@/modules/`
  import at all, no relative path that climbs above the module's folder, no
  import of the module's own index (`..` from `pages/`), which would make a
  cycle, and no `..` after a folder name (`./pages/../x`), which could hide
  a climb.
  How far a file may climb depends on its depth, so the rule comes in three
  overrides (the module's root, one folder down, two or more), and names no
  module: a new module needs no change to the configuration. A file nested
  more than two folders deep can climb only two levels.
- A module's `components/` import nothing from `@tanstack/react-query`,
  none of `useNavigate`, `useRouter`, `Navigate` or `redirect` from the
  router, none of the router's readers of route state (`useParams`,
  `useSearch`, `useLoaderData`, `useLoaderDeps`, `useRouteContext`,
  `useMatch`, `useMatches`, `useParentMatches`, `useChildMatches`,
  `useLocation`, `useRouterState`, `getRouteApi`, `RouteApi`,
  `useMatchRoute`, `MatchRoute`, `useCanGoBack`), and no `widgets/`
  (ADR 0036). `Link` and `linkOptions` stay allowed. An override for
  `src/modules/*/components/*` lists the module boundaries of its depth
  and adds these; `components/` is flat, since the override covers only
  files directly in it.
- A module's `model/` is plain TypeScript (ADR 0042): no `react` or
  `react-dom`, no `@tanstack/*`, no `@/shared/ui/` or
  `@/shared/components/`, none of the module's
  `components/`, `pages/` or `widgets/`, and from the API layer only
  `import type` (the rule's `allowTypeImports`). Its tests may also import
  the API layer's values and the fakes.
- A component's view (`components/<name>.view.tsx`, ADR 0042) imports
  nothing from `@/api/`, types included, and nothing from
  `@tanstack/react-query`; its props type comes from its state hook.
- A page file exports only its component (`react/only-export-components`),
  which keeps its load function in its own `.load.ts` file. That a load
  file imports no UI is checked in review.
- `src/shared/` imports nothing from `src/app/`, `src/routes/` or
  `src/modules/`, and from the API layer only `@/api/http`. One override,
  `src/shared/**`, covers all three of its folders: `lib/` (helpers, hooks
  and rules), `components/` (the app's own components) and `ui/`
  (shadcn's).
- Only `src/shared/` and `src/app/` import the toast component
  (`@/shared/ui/toast`, or Base UI's `Toast`); everything else reports a
  failure with `notifyError` (ADR 0041).
- The API layer's boundaries apply everywhere outside `src/api/`: a service
  only through `@/api/<service>`, no `fetch`, `openapi-fetch` or `useQuery`,
  and the fakes only from `src/mock/` and tests.
- A test (`*.test.ts`, `*.test.tsx`) has the boundaries of the code next
  to it, except that it may import the fakes and MSW through their own
  files, as may the helpers in `src/test/`; `src/shared/`'s tests keep all
  of `src/shared/`'s. Each override that sets the import rule for code is
  followed by one for its tests, which lists the same restrictions with
  `serviceIndexOnlyInMock` for `serviceIndexOnly` and without the fakes'
  and MSW's (ADR 0043).

### Component structure

[ADR 0042](docs/adr/0042-component-structure-logic-state-and-view.md),
amended by [ADR 0044](docs/adr/0044-named-values-in-components.md),
decides how a component is built inside, so that its logic can be tested
on its own and its markup with given state, without a backend
([Unit and component tests](#unit-and-component-tests)).

- **Rules and decisions are plain functions in the module's `model/`**,
  or in `src/shared/lib/` when every module's:
  validation, canonicalizing, wording, classification (`recentChange`),
  what a failed save means (`learningCardSaveFailure`), layout arithmetic
  (`itemSlots`), and the types they share. `model/` imports no React, no
  TanStack, no UI and no components, and from the API layer only types;
  lint enforces it ([Boundaries](#boundaries)).
- **A component with behavior is three files**, side by side in
  `components/`, named by suffix like a page's `.load.ts`:

  | File | Holds | Tested by |
  | --- | --- | --- |
  | `<name>.state.ts` | `use<Name>(props)`: the component's state, its data and mutation hooks, its workflows (a submit, a delete) and the values its markup needs, returned as the view's props; its return type is the view's props type | Rendering the hook against the fake backend |
  | `<name>.view.tsx` | `<Name>View`: renders its props. No data or mutation hooks, no decisions, nothing from `@/api/`; hooks that only serve rendering (refs, the virtualizer, layout measurement) are allowed | Rendering it with given props |
  | `<name>.tsx` | `<Name>`, the component other code uses: `<NameView {...useName(props)} />` | Through the other two |

  A component without behavior stays one file. Today the card form, the
  shared `ConfirmDeleteButton`, `CollectionViewSwitch` and
  `VirtualItemList` are split; the frame, the preview, the card display,
  the overview, the list and the grid (whose columns follow the window's width, which is
  layout), the card's actions (whose delete binds `ConfirmDeleteButton` to
  the card), the Markdown and the recent-change mark are not.
- **The markup reads named values.** JSX may test a named value
  (`{saveError && …}`), choose between two elements or strings on one named
  value, map a list to one component per item, and call one function in a
  one-line handler. Comparisons, arithmetic, string building and handlers of
  more than one statement don't go in the JSX: they become a named value
  above the `return`, or move to `model/` or the state hook, by the test
  below. Composing classes with `cn(BASE, flag && CLASS)` counts as testing
  a named value. Lint forbids nested ternaries (`no-nested-ternary`);
  review enforces the rest.
- **Rule or markup** (ADR 0044): would a test of the value check a rule of
  the application, or only what the markup looks like?
  - **Markup** may stay in the component, view or not, as a named value
    above the `return`: whether a slot was given, which class or element to
    use, which of two labels to show, a number formatted for display or a
    style. The frame's `hasStrip` (was a strip given) and `progressWidth`
    (the progress clamped to a CSS width) are markup: only what the frame
    renders shows them.
  - **A rule** goes to `model/`, or to the state hook when it needs React:
    limits, validation, classification (what counts as recent), wording,
    what a failure means. So does a value that uses data, mutations,
    navigation or the clock, and one that more than one component needs.
    `learningCardSaveFailure` is a rule: what a failed save means (which
    field shows which code, what is toasted, what is logged) holds whatever
    the form looks like, and its tests call it.
- **A page reads as its parts.** A choice between whole blocks of content
  is a component that makes it, such as `LearningCardsOverview`, which shows the
  empty state, the list or the grid. A handler that carries a decision,
  such as replacing the history entry, is a named function in the page
  with the reason on it, such as the overview's `handleViewChange` and
  the card page's `handleDeleted`.
- **Handlers are `handle…`, the props that take them `on…`.** A prop that
  receives a callback is `on<Event>`, or `on<Thing><Event>` when a
  component takes several (`onChange`, `onSaved`, `onDeleted`). A function
  that handles an event is `handle<Event>` or `handle<Thing><Event>`. A
  state hook defines its handlers as `handle…` and returns them under the
  view's prop names:

  ```ts
  function handleOpenChange(nextOpen: boolean) {
    if (!deleting) setOpen(nextOpen);
  }
  return { open, onOpenChange: handleOpenChange /* … */ };
  ```

  A one-line inline handler that calls one function stays inline
  (`onClick={() => void router.invalidate()}`). Review enforces the rule:
  Oxlint's `react/jsx-handler-names` doesn't fit it, since it flags a view
  passing on the `on…` props it was given, and, with inline checks, the
  one-liners.
- **UI text** is inline and in sentence case, with no extraction into
  constants or catalogs
  ([ADR 0045](docs/adr/0045-ui-text-inline-in-sentence-case.md)): a label,
  heading or message is a string in the component that shows it ("Add
  card", "Learning cards"), and moves to `model/` only when it varies with
  state or more than one component needs it, such as
  `LEARNING_CARD_FORM_TEXT`.
- **A render-prop callback renders one component.** Anything more is a
  component of its own, such as the list's `ListRow` and the grid's
  `GridCard`. Form fields are components bound to the form with TanStack
  Form's composition API: `learning-card-form-hook.ts` sets up the card
  form with `createFormHook`. `useLearningCardFormInstance` creates the
  form, and its fields render `LearningCardTextField` through
  `form.AppField`. The contexts that bind them are in
  `learning-card-form-context.ts`: the setup imports the field components,
  which read the contexts, so with the contexts in the setup the two would
  import each other.
- **Shared code moves up only when it's shared.** A hook used by one
  component lives in its `.state.ts`; one used by several of a module's
  components is its own file in `components/` (`use-<name>.ts`); one useful
  to every module goes to `src/shared/lib/`. No `hooks/` or `utils/`
  folders.

The card form, before and after. Before, one component of about 300 lines
held the save workflow in its `onSubmit` and nested its fields' render
props:

```tsx
// learning-card-form.tsx

  const form = useForm({
    onSubmit: async ({ value }) => {
      // 50 lines: canonicalize, create or update, place the API's field

  const saving = useSelector(form.store, (state) => state.isSubmitting) || mutation.isPending;
  return (
    <form onSubmit={(e) => { e.preventDefault(); e.stopPropagation(); void form.handleSubmit(); }}>
      <form.Field name="title" validators={{ onChange: validateTitle, onSubmit: validateTitle }}>
        {(title) => (
          <form.Field name="description" validators={/* … */}>
            {(description) => (
              <LearningCardFrame title={fieldSection(title, /* … */)} description={/* … */} />
            )}
          </form.Field>
        )}
      </form.Field>
      <Button type="submit" disabled={submitDisabled}>{saving ? text.submitting : text.submit}</Button>
    </form>
  );

```

After, the decisions are functions in `model/learning-card-form.ts`
(`learningCardSaveFailure`, `learningCardFieldDisplay`,
`LEARNING_CARD_FORM_TEXT`), the workflow is the state hook, and the view
renders what it returns:

```tsx
// learning-card-form.state.ts
export function useLearningCardForm({ card, cancel, onSaved }: LearningCardFormProps) {
  const form = useLearningCardFormInstance({ /* … */ onSubmit: ({ value }) => save(value) });

  // with what learningCardSaveFailure(error, mode) decides
  const title = useFieldProps(form, "title", focus); // value, label, counter, errors, invalid, active, handlers
  const description = useFieldProps(form, "description", focus);

    form, formRef, onSubmit, cancel, title, description,

// learning-card-form.view.tsx
export function LearningCardFormView({ form, title, preview, submitLabel, /* … */ }: LearningCardFormState) {
  return (
    <form ref={formRef} className={GRID} onSubmit={onSubmit}>
      <LearningCardFrame
        title={fieldSection(
          title,
          <form.AppField name="title" validators={title.validators}>
            {(field) => <field.LearningCardTextField placeholder="Enter title..." aria-invalid={title.invalid} /* … */ />}
          </form.AppField>,
        )}
        /* … */
      />
      <Button type="submit" disabled={submitDisabled}>{submitLabel}</Button>

// learning-card-form.tsx
export function LearningCardForm(props: LearningCardFormProps): ReactNode {

}
```

### Where a new file goes

| A new… | Goes in | Imported as |
| --- | --- | --- |
| Page | `src/modules/<module>/pages/<page>.tsx`, exporting only its component, exported from the module's `index.ts` | `@/modules/<module>`, by its route |
| Load function | `src/modules/<module>/pages/<page>.load.ts`, beside its page: fills what the page reads, imports only the API layer and the router, exported from the module's `index.ts` | `@/modules/<module>`, by its route's loader |
| Search params validator | `src/modules/<module>/pages/<page>.search.ts`, beside its page: checks the page's display state and fills in defaults, imports no UI, exported from the module's `index.ts` | `@/modules/<module>`, by its route's `validateSearch` |
| Component | `src/modules/<module>/components/`: data as props, outcomes as callbacks; with behavior, `<name>.state.ts`, `<name>.view.tsx` and `<name>.tsx` ([Component structure](#component-structure)) | A relative path to `<name>`, inside the module |
| Rule or decision | One module's: `src/modules/<module>/model/`, a plain function with its `*.test.ts` beside it. Every module's: `src/shared/lib/` | A relative path, inside the module, or `@/shared/lib/<name>` |
| Hook | One component's: in its `.state.ts`. Several of a module's components': `src/modules/<module>/components/use-<name>.ts`. Every module's: `src/shared/lib/` | A relative path, or `@/shared/lib/<name>` |
| Widget | `src/modules/<module>/widgets/`, created with the first one: data the page shouldn't wait for, with its own query, loading and failure | A relative path by a page, or `@/modules/<module>` by `src/app/` |
| Route | A module's page: `src/routes/<module>/`, a file named after its URL (`library/cards/new.tsx` is `/library/cards/new`): path, params, a loader that calls the page's load function, and the page. A route that belongs to no module stays at the top of `src/routes/`, next to `__root.tsx` (the root layout) and `index.tsx` (home's redirect) | Generated into `routeTree.gen.ts` |
| API call | `src/api/<service>/`: the request, its query options or mutation hook, exported from the service's `index.ts`; the fake's handler in `src/api/<service>/fake/` | `@/api/<service>` |
| Shared component | The app's own, for every module: `src/shared/components/`. A shadcn component: `src/shared/ui/`, with `npx shadcn@latest add` ([UI components](#ui-components)) | `@/shared/components/<name>` or `@/shared/ui/<name>` |
| Wording | A failure every module shares: `src/shared/lib/error-message.ts`. Anything about one module's resources: that module's `model/` | `@/shared/lib/error-message`, or a relative path |
| Module | `src/modules/<module>/` with `index.ts`, `pages/` and `components/` | `@/modules/<module>` |

#### Naming

A file or component name puts its subject first, then the variant, so a
subject's files sort together: `learning-card-edit-page`,
`learning-card-form-preview`, and `LearningCardEditPage`,
`LearningCardDeleteButton`, not `edit-learning-card-page` or
`DeleteLearningCardButton`. A function keeps its verb in front of the whole
name (`loadLearningCardEditPage`, `useLearningCardForm`).

## Development

### Getting started

The repository ships a devcontainer (`.devcontainer/`) with Go, Node, the Go
tooling (Air, Delve, goose, golangci-lint) and two PostgreSQL 18 instances:

| Service | Host port | Purpose |
| --- | --- | --- |
| `db` | `5432` | Development database (persistent volume) |
| `db_test` | `5433` | Test server (tmpfs, fsync off, for speed) |

The `app` container runs Docker's init as PID 1 (`init: true`), which reaps
the processes that tools such as the browser tests leave orphaned; without
it they would stay as zombies until the container stops.

Open the repository in the devcontainer, then:

```sh
make migrate-up   # create the schema (the server does not migrate on startup)
make dev          # Go backend with Air live reload + Vite dev server
```

| URL | What |
| --- | --- |
| http://localhost:5173 | Client app via Vite (proxies `/api` and `/docs` to the backend) |
| http://localhost:8080 | Backend directly: `/api/...`, `/docs`, and embedded client assets |

On a fresh checkout, `make dev` embeds a placeholder page in the backend; use
port 5173 for the client app. To serve a real embedded client build on port
8080, run `make build-frontend` and restart `make dev`.

Run `make` or `make help` to list every target.

Air, Delve, goose, stringer and govulncheck are tracked as tools in the separate
`backend/tools/go.mod` module, with checksums in `backend/tools/go.sum`. This
keeps tool dependencies separate from the app's dependency graph. The devcontainer
installs those pinned versions for editor and PATH access. Make targets use
`go -C backend tool -modfile=tools/go.mod` to select them while running from
`backend`. From that directory, run `go tool -modfile=tools/go.mod <tool>`, where
`<tool>` is `air`, `dlv`, `goose`, `stringer` or `govulncheck`.

To update a tool, run `go -C backend/tools get -tool <package>@<version>`, then
`go -C backend/tools mod tidy`, and commit both tool module files. Keep the goose
CLI in `backend/tools/go.mod` and library in `backend/go.mod` on the same version;
when updating goose, also run `go -C backend get github.com/pressly/goose/v3@<version>`
and `go -C backend mod tidy`, and commit both app module files.

Each tool version has one source, which the devcontainer and CI both read:

| Tool | Source | Kept in sync by |
| --- | --- | --- |
| Go | `go` line in `backend/go.mod` | `make versions-check` fails when the devcontainer's `golang:` image tag or `backend/tools/go.mod` disagrees |
| golangci-lint | `GOLANGCI_LINT_VERSION` in the `Makefile` | `make install-golangci-lint` installs it (devcontainer and CI); `make versions-check` fails when the installed binary differs |
| Node | `engines.node` (a major version, `26.x`) in `frontend/package.json` | CI's `setup-node` reads it; `make versions-check` fails when the devcontainer's node feature or the installed `node` has another major version |
| oxfmt | Exact version in `devDependencies` of `frontend/package.json`, locked in `frontend/package-lock.json` | `make frontend-deps` installs it (CI), as does the devcontainer; Make targets and the editor run that installed copy |
| Oxlint and its type-aware backend (`oxlint-tsgolint`) | Exact versions in `devDependencies` of `frontend/package.json`, locked in `frontend/package-lock.json` | Same as oxfmt |
| Playwright (`@playwright/test`) and its Chromium | Exact version in `devDependencies` of `frontend/package.json`, locked in `frontend/package-lock.json`; the browser build is the one that version expects | `make frontend-deps` and the devcontainer install both; CI caches the browser keyed by the locked version |
| Vitest (`vitest`, `@vitest/browser-playwright`, `vitest-browser-react`) | Exact versions in `devDependencies` of `frontend/package.json`, locked in `frontend/package-lock.json`; browser mode drives the `playwright` that `@playwright/test` brings, so it uses the same Chromium | `make frontend-deps` installs them, as does the devcontainer |

To upgrade Go, change all three places in one commit. To upgrade the linter,
change `GOLANGCI_LINT_VERSION` and run `make install-golangci-lint`. To upgrade
Node, change `engines.node` and the devcontainer's node feature in one commit,
then rebuild the devcontainer. To upgrade oxfmt, which can change formatting,
change its pin, run `npm install` in `frontend/` and `make frontend-fmt`, and
commit the reformat on its own. To upgrade Oxlint, which can add rules, change
the pins of `oxlint` and `oxlint-tsgolint` together, run `npm install` in
`frontend/` and `make frontend-lint`, and fix or configure what it reports in
the same change. To upgrade Playwright, change its pin, run `npm install` and
`make frontend-deps` (which downloads the new browser once), and run both kinds
of [browser test](#browser-tests) and `make frontend-unit`. To upgrade Vitest,
change the pins of `vitest` and `@vitest/browser-playwright` together (they
release in lockstep), run `npm install` and `make frontend-unit`.

The API type generator (`openapi-typescript`) needs TypeScript 5's JavaScript
API, while the client app uses TypeScript 7, so it lives in its own package,
`frontend/tools/`, with exact pins and its own lockfile
([ADR 0031](docs/adr/0031-generated-api-types-and-typed-fetch-client.md)).
`make frontend-deps` installs the locked dependencies of both packages.

### Running without the backend

```sh
make dev-mock     # Vite dev server only; a fake backend answers /api in the browser
```

Open http://localhost:5173. [MSW](https://mswjs.io) intercepts the client
app's API requests and answers them from in-memory fakes in
`frontend/src/api/<service>/fake/`, so no Go server, database or migrations
are needed. The fake implements only what the client app's flows depend on:
state across requests, not found, malformed IDs, opaque cursors and minimal
validation (trimmed, required, maximum length, page size). It doesn't
reproduce the backend's input parsing
([ADR 0032](docs/adr/0032-stateful-fake-backend-with-msw.md)). An API request
the fake has no handler for fails as a network error, with the request named
in the console, instead of reaching a server. The mock mode doesn't proxy to
the backend, so the API reference at `/docs` isn't available there. While the
browser is offline (the Network panel's "Offline" in the developer tools, or
Playwright's `context.setOffline`), the fake fails every API request as a
network error; MSW's worker answers requests from inside the page, so it
would otherwise keep answering them.

Query parameters on the URL the app loads with choose the data:

| Parameter | Effect |
| --- | --- |
| `scenario=default` | About eight cards with varied markdown (also when omitted) |
| `scenario=empty` | No cards |
| `scenario=many` | 150 cards, more than one page |
| `scenario=failing` | Every API request answers `500 unexpected_error` |
| `delay=<ms>` | Adds that many milliseconds to every API response, for example `?scenario=many&delay=2000` |

The fake's state lives in the page's memory: changes survive navigation
inside the app, and reloading the page starts over from the parameters in
the address bar. In-app links drop them, so a reload after navigating starts
the default scenario. Seeded cards get new IDs on every load, so a card's
URL, such as its editor, shows "doesn't exist" after a reload. Each tab
runs its own fake, so a change made in one tab is invisible to another. To
see the last write win, open a card's editor, change the card from the
browser console, then save: the form's values replace the change.

```js
const id = location.pathname.split('/').at(-2) // /library/cards/<id>/edit
const card = await (await fetch(`/api/lcards/${id}`)).json()
await fetch(`/api/lcards/${id}`, {
  method: 'PUT',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ title: 'Changed elsewhere', description: card.description }),
})
```

Production builds contain neither MSW's worker nor the fake.

### UI components

The client app's UI components come from [shadcn/ui](https://ui.shadcn.com),
copied into `frontend/src/shared/ui/` and maintained there like the rest
of the code. `frontend/components.json` configures the shadcn CLI: its
aliases point at `src/shared/ui/` for components and `src/shared/lib/` for
helpers and hooks, so the CLI writes there. `src/shared/ui/` holds only
shadcn's components; the app's own shared components go in
`src/shared/components/`. To add a component, run from
`frontend/`:

```sh
npx shadcn@latest add <component>
```

The components use [Phosphor](https://phosphoricons.com) icons. The CLI
imports them from the package's main entry, `@phosphor-icons/react`, which
`make frontend-lint` rejects. Import each icon from its own module instead,
as Phosphor recommends:

```tsx
import { CaretLeftIcon } from "@phosphor-icons/react/dist/csr/CaretLeft";
```

In development, Vite pre-bundles the main entry as a single module of every
icon (over 6 MB), and evaluating it blocks the page for up to seconds on a
slow machine. A production build includes only the icons used either way.

The CLI runs from npm's cache, so it doesn't need a `shadcn` package in
`package.json`. The components rely on CSS that shadcn ships as
`shadcn/tailwind.css`: shared keyframes, custom variants such as `data-open:`,
and the `scroll-fade` and `shimmer` utilities. That CSS is ejected into
`frontend/src/styles/shadcn.css`, whose first line names the shadcn version it
came from, and `global.css` imports it. This keeps the `shadcn` package and its
dependency tree (an MCP server, an HTTP framework, ts-morph) out of the app's
dependencies and out of its [vulnerability scan](#vulnerability-scan).

When updating components to a newer shadcn version, refresh the ejected CSS in
the same change. From `frontend/`:

1. In `src/styles/global.css`, replace `@import "./shadcn.css";` with
   `@import "shadcn/tailwind.css";`.
2. Run `npm install shadcn@<version>`, then `npx shadcn@<version> eject --yes`.
   Eject reads the CSS from the installed package, inlines it into
   `global.css` after an `/* ejected from shadcn@<version> */` line, and
   uninstalls the package.
3. Move the ejected block, from that line up to the `@fontsource-variable`
   imports, into `src/styles/shadcn.css` in place of its contents, and restore
   the `./shadcn.css` import.
4. Run `git checkout package.json package-lock.json` and `npm ci`: the install
   in step 2 can also move unrelated locked versions.
5. Run `make frontend-fmt`, then `make frontend-test`, and review the diff of
   `shadcn.css`.

### GitHub CLI in the devcontainer

Agents open pull requests with `gh`, authenticated by `GH_TOKEN`, which the

Out-of-scope findings become issues from the

1. Create a fine-grained token limited to this repository, with

   the token can open pull requests and issues but cannot push or merge.
2. Save it to `~/.config/ludustudii/gh_token` (`chmod 600`) and export it from


3. Log out and back in, then rebuild or reopen the container.
   `gh auth status` inside the container should report the token.

Without `GH_TOKEN`, everything else works; agents just can't open pull
requests or issues.

### Testing

Unit tests use `<name>_test.go`; integration tests use
`<name>_integration_test.go`. Service API tests keep `api_test.go` as the
exception. Filenames identify the scope; retain the `unit` and `integration`
build tags to select which suite runs. `make test-tags-check` (part of
`make check`) fails when a test file's name and build tag disagree.

Tests are split by build tag:

| Command | Tag | Scope |
| --- | --- | --- |
| `make test-unit` | `unit` | Handlers, validation, kit, spec, fuzz contracts, with `-race`. No database. |
| `make test-integration` | `integration` | Stores and API tests against real PostgreSQL, with `-race` |
| `make test` | both | Everything |
| `make coverage` | `unit,integration,apidocs` | All backend tests with `-race`; writes `backend/coverage/coverage.out` and `backend/coverage/coverage.html`. Requires `DB_TEST_CONNECTION`. |

Both test targets accept `PKG` (default `./...`, relative to `backend`) and
`RUN` (a Go test name regex, default all tests). They use `-race`, `-count=1` and
`-shuffle=on` to detect races and dependencies on test order.

```sh
make test-integration PKG=./internal/services/lcards/... RUN=TestCreate
make test-unit PKG=./internal/services/lcards/create RUN='Test.*'
```

The extra unit-test run with the `apidocs` tag runs only when `PKG` includes
that package, and uses the same `RUN` filter.

To view the coverage report from the devcontainer, run this from the repository
root:

```sh
python3 -m http.server 8000 --directory backend/coverage
```

Forward port 8000 in VS Code's **Ports** tab, then open the forwarded URL with
`/coverage.html`. Stop the server with Ctrl+C when finished.

The testing strategy is deliberate:

- **Handler tests** (`handler_test.go`, unit) replace each step — bind, validate, store — through
  function fields and interfaces, so every step is tested in isolation.
- **Store tests** (`store_integration_test.go`, integration) run real SQL against a real database; stores
  have no unit tests or mocks.
- **API tests** (`api_test.go`, integration) drive the full router over HTTP with a real
  client and database, covering routing, middleware and error handling.
- **Contract tests** fuzz the sanitizer against the validators, so sanitized
  input always passes the format checks.

`testkit` makes integration tests isolated and parallel-safe: on first use it
creates a template database on `DB_TEST_CONNECTION` and migrates it, then gives
every test its own `CREATE DATABASE ... TEMPLATE` clone, dropped when the test
ends. Packages with integration tests opt in from `TestMain`:

```go
func TestMain(m *testing.M) {
	os.Exit(testkit.Run(m))
}
```

Every response received through `testkit.Do` is validated against the OpenAPI
spec (status, headers and body schema), so the implementation and the spec
can't drift apart unnoticed.

#### Unit and component tests

[Vitest](https://vitest.dev) runs the client app's unit and component tests
([ADR 0043](docs/adr/0043-unit-and-component-tests-with-vitest.md)).
`frontend/vitest.config.ts` builds them with the app's Vite config, so
imports, aliases and plugins behave as in the app. A test sits next to the
file it tests, and its name decides where it runs:

| File | Vitest project | Runs in | For |
| --- | --- | --- | --- |
| `<name>.test.ts` | `unit` | Node, without a DOM | Plain functions: a module's `model/`, the logic in `src/shared/lib/` |
| `<name>.test.tsx` | `browser` | Chromium's headless shell, through Playwright, the one `make frontend-deps` installs | State hooks, rendered with `renderHook`, and views, rendered with `render`, both from `vitest-browser-react` |

The client app's test layers, lowest first:

| Layer | Covers | Doesn't cover |
| --- | --- | --- |
| `model/` tests | Every rule and its edge cases | Rendering |
| State hook tests | Workflows: what a submit or delete does on success and failure, the values the view gets | Markup |
| View tests | Each state the view can show, from given props: labels, disabled controls, errors, empty states | Data, navigation |
| Playwright mock ([Browser tests](#browser-tests)) | Flows across pages: navigation, history, scroll restoration, virtualization, layout | Single rules and states |
| Playwright e2e | Success paths against the real backend | Edge cases |

A check belongs to the lowest layer that can make it: a field's message for
one code is a `model/` test, not a page, a form and a submit in Playwright.

```sh
make frontend-unit                                              # every test, as make check runs them
make frontend-unit ARGS='src/shared/lib/field-errors.test.ts'   # one file (or a folder)
make frontend-unit ARGS='--project unit -t canonicalize'        # Node tests whose name matches
cd frontend && npx vitest                                       # watch mode: reruns what a change affects
```

`make frontend-unit` fails on a `test.only` left behind. A failed browser
test leaves a screenshot in `frontend/.vitest/attachments/`.

**Browser tests run against the fake backend**
([ADR 0032](docs/adr/0032-stateful-fake-backend-with-msw.md)), started in
the test page with MSW's service worker by `src/test/setup.browser.ts`, with
the same handlers as the mock mode; an API request the fake has no handler
for fails as a network error. The network is the seam: a test seeds the
fake through its own modules (`cardStore.seed(makeCards(3))`) and changes
what it answers with `fakeBackend.use(...)` from `src/test/fake-backend.ts`,
rather than mocking the API layer. Use `vi.mock` only for what isn't the
network, and Vitest's fake timers (`vi.useFakeTimers()`) for the clock.
Test files and `src/test/` may import the fakes and MSW, except in
`src/shared/`, which knows no service; every other boundary of the code
next to them applies ([Boundaries](#boundaries)).

**Each test is isolated.** After every test the fake's stores are emptied,
the handlers a test added are removed, and TanStack Query takes the browser
to be online again (`goOffline` in `src/test/online.ts` takes it offline).
`renderWithProviders(ui, { url })` and `renderHookWithProviders(hook)` in
`src/test/render.tsx` render with a new query client with the app's
defaults (retries without the delay), and, given a `url`, in a router, for
a component that renders links. Everything
renders in React's `StrictMode` and with the app's styles, as the app does. A test finds elements by
role, label and text, as the Playwright tests do.

The mock mode stays out of these builds: `msw()` from `msw/vite` and
`virtual:msw` are only in the app's config in the mock mode, which
`vitest.config.ts` refuses, and the tests' config leaves out the dev
server's proxy, so a request the fake misses never reaches a running
backend. It serves MSW's worker script itself, and nothing else of the mock
mode.

A test that waits for a suspending query, such as a component reading the
cards, takes about 0.8 s: React shows suspended content after 300 ms, as in
the app, and the locator retries on a backoff. A view test with given props
takes milliseconds.

#### Browser tests

[Playwright](https://playwright.dev) drives the client app in Chromium
([ADR 0034](docs/adr/0034-browser-tests-with-playwright.md)). There are two
kinds, each in its own folder under `frontend/tests/` and its own Playwright
project:

| Command | Tests | Runs against | Covers | Runs in |
| --- | --- | --- | --- | --- |
| `make frontend-test` | `frontend/tests/mock/` | The client app in the mock mode, port 5183, with the [fake backend](#running-without-the-backend); no Go server or database. On Vite's dev server, or on a build of the mock mode with `MOCK_BUILD=1`, as CI runs it | Flows across pages and what only the whole app shows: create, edit, delete and cancel and where each ends, Back after a create or a delete, a card deleted or changed elsewhere, the view in the URL and the history, the overview's virtualization (rendering only what is near the window, tabbing through the actions, Back to the same position), routing and not-found pages, the error and pending pages, the navigation's progress bar, one heading and one main landmark per page, and layout at a viewport size (the grid's columns, cut titles, the editor and its preview, where a toast sits) | `make check` |
| `make test-e2e` | `frontend/tests/e2e/` | The built binary with the client app embedded, port 8183, on a database made for the run | Success paths through the real API and database: create a card and land on its page, find it in the list, edit it and land on its page, find it in the grid and open it, delete it on its page; open a card's page and its editor by URL; a nonexistent card | Its own CI job |

Both targets pass `ARGS` on to Playwright, for example
`make frontend-test ARGS='--repeat-each=5'` or `make test-e2e ARGS='-g URL'`.
Run a new or changed test with `--repeat-each=5` before opening a pull request;
a test that fails only sometimes is a broken test.

**The budget: `make check` runs in under 5 minutes on CI**, the `make check`
job from checkout to its end. The app tests are its slowest step, a page
load or more each, so **a new app test is only for a flow across pages**.
A rule, or a state that one page or component can show, goes to the lowest
[Vitest layer](#unit-and-component-tests) that can check it, where it takes
milliseconds. A change that takes the job past the budget first moves
checks down a layer or makes the slow tests faster.

`make test-e2e` builds the client app and the binary, creates a database with
a unique name (`ludustudii_e2e_<time>_<random>`) on the server in
`DB_TEST_CONNECTION` with `psql` (the devcontainer installs it; GitHub's
Ubuntu runners have it), migrates it with goose and runs the tests. The binary
gets that database's URL from `E2E_DB_CONNECTION`, so running the end-to-end
config without the target fails with a hint. The database is dropped
afterwards, also when a test fails or the run is interrupted with Ctrl+C.

Each kind has its own config, `frontend/playwright.mock.config.ts` and
`frontend/playwright.e2e.config.ts`, with the shared settings in
`frontend/tests/playwright.base.ts`. Playwright starts every web server a
config declares, whichever project runs, so one config per kind is what keeps
the app tests from building or starting the Go server, and the end-to-end
tests from starting Vite. Each starts its own server on a port that
`make dev` doesn't use, and never reuses one already running. Both run
Chromium's headless shell only, with every test in parallel, and no retries,
so a flaky test fails instead of passing on its second try. Workers are
Playwright's default of half the CPU cores, or `PLAYWRIGHT_WORKERS` when it
is set, capped at one per GB of free memory: each worker's Chromium takes up
to about 650 MB, and a renderer that runs out of memory crashes its page. CI
sets `PLAYWRIGHT_WORKERS=3` for the app tests: on its 4-core runner, 3
workers ran them faster than 2 or 4. A failed test keeps its trace and
screenshot; the HTML report is in `frontend/playwright-report/<kind>/`, and
`npx playwright show-report playwright-report/<kind> --host 0.0.0.0` in
`frontend/` serves it on port 9323.

**App tests** get a new page each, and with it a fresh fake, so they run in
parallel and can rely on the scenario's data, totals included. The fake's
state lives in the page, so a test moves between pages with the app's links;
`page.goto` reloads the page and starts the fake over. Scenarios come from
the URL (`/library/cards?scenario=empty`), and other states from inside the
page: `deleteCardElsewhere` in `tests/support/cards.ts` deletes a card with
a `fetch` the fake answers, as another tab would, so the page's copy no
longer matches it. `context.setOffline(true)` makes the fake fail requests
as the network would.

**Tests don't wait for real time to pass.** A test that checks what a page
shows while a request is pending holds that request with `holdRequests` in
`tests/support/fetch.ts` and lets it through with `releaseRequests`, so the
pending state lasts as long as the test looks at it; one that checks that
nothing happens meanwhile, such as a request, watches for a few frames. Timers, such
as a query's retries or the router's pending delay, run on Playwright's
clock (`page.clock.install()` before `page.goto`), which the test moves on
with `page.clock.fastForward` or, when it can't see when a timer starts,
`fastForwardUntil` in `tests/support/clock.ts`. A test that measures where
something ends up emulates reduced motion, so nothing slides there first.
The mock mode's `delay` URL parameter is for trying a slow server by hand.

**End-to-end tests** share one database and run in parallel, so every test
creates its own data with a unique title (a random UUID in it) and asserts only
on that data, never on totals or positions. The overview is newest first,
and another test may create a card at any moment, so a test doesn't assume
its card is the first item. It finds the card by title with `findCard` in
`tests/support/overview.ts`, which scrolls down a screen at a time until
the overview has rendered it, or it opens the card by its ID (from its
page's URL, or the `Location` of a card created through the API). The
overview loads only its first page (100 cards), so a test deletes the cards
it creates, which keeps the other tests' cards on that page.

**Locators** find elements the way users do: by role, label and text
(`getByRole`, `getByLabel`, `getByText`). A test that fails because an element
lost its accessible name has found a real problem. A test ID is a last resort,
for an element with no role, label or text a user would know it by, and its
use says why in a comment. The overview renders only the items near the
window, so a test reaches an item by its position among all the cards
(`cardAt` in `tests/support/overview.ts`, from its `aria-posinset`) or its
title (`cardItem`), and scrolls the window (`scrollWindow`) to bring others
in.

**A new feature adds its tests** in the same pull request: [unit and
component tests](#unit-and-component-tests) for its rules, state hooks and
views, error paths included, next to them; app tests only for its flows
across pages, in `tests/mock/<feature>.spec.ts`, with the fake
extended for what they need ([ADR 0032](docs/adr/0032-stateful-fake-backend-with-msw.md));
an end-to-end test for its main success path, with uniquely named data, in
`tests/e2e/<feature>.spec.ts`; and steps both kinds share in `tests/support/`.
Tests are TypeScript, type-checked by `make frontend-typecheck` (with
`frontend/tests/tsconfig.json`), and linted and formatted like the client app.

`make frontend-deps` installs Chromium's headless shell in the version the
locked `@playwright/test` expects; it does nothing when that version is
present. The devcontainer runs the same install in `post-create.sh`, into the
`playwright-browsers` volume at `/ms-playwright` (`PLAYWRIGHT_BROWSERS_PATH`),
so a rebuild keeps the browser. Chromium's system libraries, which the
`golang` image lacks, are packages in the container: `post-create.sh` installs
them with `npx playwright install-deps chromium` on every rebuild, as CI does.
A devcontainer created before these changes needs a rebuild; until then, run
`make frontend-deps` and `npx playwright install-deps chromium` in `frontend/`,
and the browser goes to Playwright's default cache, `~/.cache/ms-playwright`.

### API spec and reference

The spec is split across `backend/apispec/openapi.yml`, `paths/` and
`components/`. The reference page serves a single bundled copy at
`backend/internal/infra/apidocs/dist/openapi.json`, which is committed.

- `make spec-bundle` regenerates the bundle when a spec file changed. Air runs
  it on every rebuild during `make dev`.
- A unit test fails if the committed bundle is stale.
- `make api-types` generates the client app's types,
  `frontend/src/api/schema.gen.ts`, from the bundle. The file is committed;
  `make api-types-check` fails when it is stale. After a spec change, run
  `make api-types` and commit the bundle and the types together. If the
  client app calls the endpoint, update its fake as well
  ([Running without the backend](#running-without-the-backend)).

The reference UI is the Scalar standalone script, taken from
`frontend/node_modules`, gzipped and embedded only when building with the
`apidocs` tag. It is fully self-hosted (no external fonts or AI agent). If the
tag is set but the script is missing, the server logs a warning and starts
without `/docs`.

### Logs

`make dev` appends the backend's JSON logs to `backend/tmp/app.log` (override
with `LOG_FILE=...`). These targets query it with `jq`:

| Command | Purpose |
| --- | --- |
| `make logs` | Follow and pretty-print the log |
| `make logs-errors` | `ERROR` and `WARN` records |
| `make logs-req ID=<request id>` | Every record for one request |
| `make logs-slow MS=500` | Requests slower than `MS` ms (default 200) |
| `make logs-stats` | Request counts by status, method and route |

Each request produces one `request` record with method, route, path, status
and latency, logged at `ERROR` for 5xx, `WARN` for 4xx and `INFO` otherwise.
The quiet probe paths `/livez` and `/readyz` log their summaries at `DEBUG`
regardless of status. Readiness logs state transitions once: `WARN` with the
reason when becoming unavailable, `INFO` on recovery, and `INFO` when stopping
starts. Repeated failed probes do not repeat the warning.

`make check` runs `versions-check`, `fmt-check`, `frontend-fmt-check`,
`test-tags-check`, `pr-title-check-test`, `lint`, `tidy-check`,
`generate-check`, `api-types-check`, `frontend-typecheck`, `frontend-lint`,
`frontend-unit`, `frontend-test`, `test-unit` and `test-integration` sequentially, stopping at
the first failure. It needs the frontend dependencies and Playwright's
Chromium (`make frontend-deps`). The end-to-end tests (`make test-e2e`) aren't
part of it; CI runs them in their own job.

`make generate-check` includes the committed OpenAPI bundle. It leaves regenerated
files on disk for review and ignores pre-existing edits that generation leaves unchanged.

Lint uses the `unit,integration,apidocs` build tags so tests are included.
The alternate `script_none.go` build is intentionally omitted from linting.

oxfmt formats the client app with its defaults
([ADR 0033](docs/adr/0033-oxlint-and-oxfmt-for-the-client-app.md)).
`frontend/.oxfmtrc.json` sets two options beyond them:

- `sortImports` sorts import statements with oxfmt's default groups,
  separated by a blank line: Node.js built-ins, packages, `@/` imports,
  relative imports, then style imports. It doesn't reorder side-effect
  imports. A comment directly above an import moves with it, so a file's
  header comment ends with a blank line before the imports.
- `sortTailwindcss` sorts Tailwind classes in `class` and `className`
  attributes and in `cn` and `cva` calls, in the order of the theme in
  `src/styles/global.css` (without it, the theme's classes such as
  `text-muted-foreground` sort as unknown).

It also ignores the generated files (`src/api/schema.gen.ts`,
`src/routeTree.gen.ts`) and the lockfiles. In the devcontainer, the Oxc
extension formats JavaScript, TypeScript and CSS files on save.

`.git-blame-ignore-revs` lists formatting-only commits, so blame shows the
change before them. GitHub's blame view uses it automatically; locally, run
`git config blame.ignoreRevsFile .git-blame-ignore-revs` once per clone. Every
later formatting-only commit adds its hash to the file.

Oxlint lints the client app with type-aware rules, configured in
`frontend/oxlint.config.ts` (ADR 0033, ADR 0037): the correctness and suspicious
categories as errors, the promise and React hooks rules, `no-nested-ternary` (ADR 0042), and the module
boundaries as `no-restricted-imports` per directory. Outside `src/api/`, code
imports a service only through `@/api/<service>` (plus the shared files
directly in `src/api/`), doesn't call `fetch` or import `openapi-fetch`,
`useQuery`, `useMutation` and similar hooks, and only `src/mock/` imports the
fakes. Modules, `src/shared/` and the code around them keep the boundaries
of ADR 0035 ([Client app → Boundaries](#boundaries)). Inside `src/api/`, only the fakes themselves (`src/api/fake.ts` and the
`fake/` folders) import the fakes, `msw` or `openapi-msw`, which keeps them out
of the production bundle (ADR 0032). Everywhere, Phosphor icons come from their own modules, not the
package's main entry ([UI components](#ui-components)). Every rule turned off carries its reason in the configuration.

The configuration is TypeScript so that each import restriction is written
once: a named constant with its message and its ADR. An override replaces a
rule's options instead of merging them, so each override lists, by name,
every restriction that applies to its files, and `restrictImports` puts each
in `paths` or `patterns`, keeping their order. A new boundary is one constant, added by name to
each override that needs it. Keep the file a list of rules: plain constants
and arrays, no loops or generated regexes. `make frontend-typecheck` checks it
against Oxlint's `defineConfig` types, and Node runs it by stripping the
types, so it uses only syntax that strips (`erasableSyntaxOnly`). In the
devcontainer, the Oxc extension applies the same configuration through its
`oxc.configPath` and `oxc.path.tsgolint` settings.

#### Exclusion policy

Use `backend/.golangci.yml` for shared rules: generated files and bundled assets,
standard exclusion presets, test fixtures, and package boundaries.

For a one-off exception, place `//nolint:<linter> // <reason>` beside the code
with the smallest practical scope. Name the linter and explain the deliberate
behavior or false positive; prefer a real fix when the finding identifies a bug.
For gosec, use `// #nosec Gxxx -- <reason>` to suppress only the relevant check.

In the client app, a one-off exception is
`// oxlint-disable-next-line <plugin>/<rule> -- <reason>`, only where the rule
is wrong for that code. Never disable a promise rule: await or return the
promise where the caller must wait for it, or mark it `void` with a comment
saying why not waiting is right. `make frontend-lint` fails on a disable
directive that no longer suppresses anything.

### Vulnerability scan

`make vuln` runs govulncheck on the backend, then `make frontend-vuln`, which
runs `npm audit` on the lockfiles of `frontend/` and `frontend/tools/`. Both
depend on an external vulnerability database, so they stay out of
`make check` and run on a schedule instead
([ADR 0020](docs/adr/0020-pinned-tooling-and-single-quality-gate.md)).
`npm audit` reads only the lockfiles, so it doesn't need `node_modules`.

The thresholds follow where the code runs. The client app's production
dependencies (`npm audit --omit=dev`) ship to every user's browser, so a
moderate advisory fails the scan. Its dev dependencies and the generators in
`frontend/tools/` run only on developer machines and in CI, so only a high or
critical one does. Lower advisories still appear in the output.

When an advisory fails the scan, upgrade the package that pulls in the
vulnerable version. If no fixed version exists yet, or the direct dependency
hasn't adopted one, either add an
[`overrides`](https://docs.npmjs.com/cli/configuring-npm/package-json#overrides)
entry to that `package.json` that forces a patched transitive version (run
`npm install`, then the tests, and remove the entry once the dependency
catches up), or wait for a fix and track it in an issue; the scheduled scan
keeps failing until then.

### CI

GitHub Actions runs the same gate as a developer
([ADR 0028](docs/adr/0028-ci-reuses-the-devcontainer-test-database.md)):

| Workflow | When | What |
| --- | --- | --- |
| [`ci.yml`](.github/workflows/ci.yml) | Every push to `main` and every pull request; a newer push to a pull request cancels its older run, while runs on `main` always finish | `make check`, and `make test-e2e` in a second job beside it |
| [`pr-title.yml`](.github/workflows/pr-title.yml) | Every pull request when it is opened, reopened, pushed to or edited, so fixing the title re-runs it | `make pr-title-check` with the pull request title, which must be `type: summary` within 64 characters |
| [`vuln.yml`](.github/workflows/vuln.yml) | Daily at 03:17 UTC, or on demand | `make vuln`: govulncheck and `npm audit`, with Go from `backend/go.mod` and Node from `engines.node` (no npm install) |

Both `ci.yml` jobs set up their tools with the same steps, in
[`.github/actions/setup`](.github/actions/setup/action.yml): Go from
`backend/go.mod`, Node from `engines.node` in `frontend/package.json`, the
frontend dependencies and Playwright's Chromium with `make frontend-deps`, and
Chromium's system libraries with `npx playwright install-deps chromium`. The
browser directory is cached, keyed by the Playwright version in
`frontend/package-lock.json`, so only an upgrade downloads it. The `check` job
also installs golangci-lint with `make install-golangci-lint`. Each job starts
only `db_test` from `.devcontainer/docker-compose.yml`
(`docker compose up -d --wait db_test`) and points `DB_TEST_CONNECTION` at
`localhost:5433`. When a job fails, its Playwright report, with the traces and
screenshots of the failed tests, is uploaded as an artifact
(`playwright-report-mock` or `playwright-report-e2e`) on the run's page.

A failing `ci.yml` run means the change isn't done. To run the vulnerability
scan by hand, open **Actions → Vulnerability scan → Run workflow**, or run
`gh workflow run vuln.yml`.

To report a vulnerability, follow [SECURITY.md](SECURITY.md).
