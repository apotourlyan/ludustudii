Ludus Studii ("The Study Game") — Turn complex study material into structured, gamified learning loops.

## Backend

A single Go binary serves the JSON API under `/api`, the embedded React client
app, root-level operational probes, and (optionally) an interactive API
reference under `/docs`.

### Stack

| Area | Choice |
| --- | --- |
| Language | Go 1.27 |
| HTTP | `net/http` + `http.ServeMux` |
| Database | PostgreSQL 18 via `database/sql` + [pgx](https://github.com/jackc/pgx) (no ORM, hand-written SQL) |
| Migrations | [goose](https://github.com/pressly/goose), SQL files embedded in the binary |
| IDs | UUIDv7 generated by PostgreSQL (`uuidv7()`), so ID order is creation order |
| Logging | `log/slog`, JSON or text, with per-request IDs |
| API contract | OpenAPI 3.0 in `backend/apispec`, validated with [kin-openapi](https://github.com/getkin/kin-openapi) |
| API reference | [Scalar](https://github.com/scalar/scalar), self-hosted and embedded behind a build tag |
| Live reload | [Air](https://github.com/air-verse/air) |

### Layout

```
backend/
├── cmd/
│   ├── server/api/        # main: the HTTP server
│   └── tools/bundlespec/  # bundles the OpenAPI spec into one JSON file
├── apispec/               # OpenAPI spec (openapi.yml, paths/, components/), embedded
├── migrations/            # goose SQL migrations, embedded (see goose.md)
├── tools/                 # separate module for pinned development tools
└── internal/
    ├── app/               # composition root: config, logger, DB; composes the surfaces (handler.go)
    │   ├── api/           # API surface: every service under /api
    │   ├── router/        # shared HTTP front: root mux, middleware chain, central error handler
    │   └── server/        # process lifecycle: serve, drain, graceful shutdown
    ├── infra/             # env, health (probes), logging, rdb (Postgres), spa (client app), apidocs
    ├── kit/               # helpers independent of app and infra: erresp, validator, sanitizer, staticfile, httpkit
    ├── services/
    │   └── lcards/        # learning cards: one subpackage per endpoint
    │       ├── domain/    # shared rules, limits and constants
    │       ├── create/    # handler.go + store.go
    │       ├── get/
    │       ├── list/
    │       ├── update/
    │       └── remove/
    └── testkit/           # test-only helpers: isolated DBs, HTTP client, OpenAPI checks
```

Each endpoint is a vertical slice with its own `Handler` and `Store`. A handler
binds, sanitizes and validates the request, then calls its store through a
small interface. Each store query lives in its own `.sql` file beside `store.go`,
with a header comment listing its placeholders, and is embedded with `//go:embed`.
Stores contain no inline SQL strings. Package boundaries are enforced by `depguard`:

- `kit` must not import `infra`, `services` or `app`.
- `services` must not import `infra` or `app`.
- `app/router` and `app/server` must not import the rest of `app`, `services`,
  any surface (`health`, `spa`, `apidocs`) or `rdb`, including from their tests.
- The surfaces (`app/api`, `health`, `spa`, `apidocs`) must not import the rest
  of `app`, each other, `env` or `rdb`, including from their tests.
- `testkit` may only be imported from test files.

#### Surfaces and startup

The HTTP server is composed of surfaces. Each is built on its own, owns its
patterns on one root `http.ServeMux` and needs only its own dependencies:

| Surface | Patterns | Built by | Needs |
| --- | --- | --- | --- |
| Probes | `/livez`, `/readyz` | `health.NewProbes` | readiness state |
| API | `/api`, `/api/` | `api.New` (`internal/app/api`) | database |
| API reference | `GET /docs`, `GET /docs/{$}`, `GET /docs/openapi.json`, `GET /docs/scalar.js` | `apidocs.NewHandler`, only when enabled | embedded files |
| Client app | `/` (catch-all) | `spa.NewHandler` | embedded files |

A surface implements `router.Surface` (`Mount(*http.ServeMux)`). `router.New`
mounts the surfaces it is given and wraps the root mux once with the
middleware chain; it knows no surface. Surfaces that platforms poll also
implement `router.QuietSurface`, so their request summaries log at debug.
Every surface reports errors to the same `router.ErrorHandler`.

`internal/app` is the composition root and the only package that knows every
surface. `app.Run` loads the configuration, the client app, the optional
reference and the database. `newHandler` (`internal/app/handler.go`) builds the
surfaces and mounts them, and `server.Run` owns the process lifecycle:
serving, draining and graceful shutdown. Tests compose only the surfaces they
need. Service API tests mount the API surface alone, for example. A future
binary that serves a subset of the surfaces needs a new composition root, not
changes to the surfaces ([ADR 0001](docs/adr/0001-single-binary-services-as-packages.md)).

#### Routing

The root mux sends `/api` and `/api/` to an `httpkit.API`, which has its own
mux for the API routes. Both muxes serve requests themselves, so they set
`Request.Pattern` and wildcard path values (`r.PathValue("id")`).

- **API endpoints** register with `api.HandleFunc`, one call per method and
  path, in each service's `routes.go`. Each service's `RegisterRoutes` is
  called from `api.New`:

  ```go
  api.HandleFunc("GET "+domain.CardsPath+"/{id}", g.Handle)
  api.HandleFunc("PUT "+domain.CardsPath+"/{id}", u.Handle)
  api.HandleFunc("DELETE "+domain.CardsPath+"/{id}", d.Handle)
  ```

  Patterns always include the method, and GET also serves HEAD. Literal
  segments such as `/api/lcards/due` can sit next to `/api/lcards/{id}`.
- **Unknown API paths and methods** are decided by the API mux. `httpkit.API`
  runs the mux's own 404 or 405 handler against a probe and reports
  `not_found`, or `method_not_allowed` with the mux's `Allow` header (methods
  sorted alphabetically, across every pattern that matches the path). An `/api`
  path never reaches the SPA.
- **Probes** reserve `/livez` and `/readyz` outside the API and the SPA. GET
  also serves HEAD; other methods receive JSON `405 method_not_allowed` with
  `Allow: GET, HEAD`.
- **`/docs`** routes are `GET` patterns, registered only when the reference is
  enabled; other methods fall through to the SPA.
- **The SPA** is the method-less `/` catch-all and answers non-GET/HEAD
  methods with a plain-text `405`. It cannot be `GET /`, which conflicts with
  `/api/`.
- Paths with `//`, `.` or `..` segments get the mux's `307` redirect to the
  cleaned path.

The request log's `route` is the matched mux pattern, for example
`GET /api/lcards/{id}`, `/api/` for an unknown API path or method (`/api` for
the bare path), or `/` for the SPA. It is empty when middleware rejects a request
before routing, such as a `413` for a declared body over the limit.

Handlers return failures to the app's central error handler, which writes the
shared JSON error shape. `httpkit` request errors retain their causes and named
responses; `kit.ErrNotFound` and `kit.ErrVersionConflict` map to 404 and 412.
Status errors carry their own status and response body and are logged at debug
level. All other errors are logged at error level and returned as a generic 500.
Handler function fields remain the seams for isolating binding and validation
in unit tests.

Production environment variables are read only in `internal/infra/env`; the
`testkit` harness reads `DB_TEST_CONNECTION` directly. Application logging goes
through `log/slog` (`fmt.Print*` and `log.*` are forbidden by the linter).

### API

| Method | Path | Description | Success |
| --- | --- | --- | --- |
| `GET` | `/api/lcards` | List cards, newest first, keyset-paginated | `200` |
| `POST` | `/api/lcards` | Create a card | `201` + `Location` header |
| `GET` | `/api/lcards/{id}` | Get a card | `200` |
| `PUT` | `/api/lcards/{id}` | Replace a card's title and description | `204` |
| `DELETE` | `/api/lcards/{id}` | Delete a card | `204` |

`HEAD` is supported wherever `GET` is. The OpenAPI spec in `backend/apispec`
is the source of truth; the notes below summarize it.

- **Requests** with a body must use `Content-Type: application/json` (otherwise
  `415`). Bodies are limited to 1 MiB (`413`). Unknown JSON fields are rejected
  with `400 bind_error`.
- **Input** strings are normalized to Unicode NFC and trimmed before
  validation. Title is 1–200 and description 1–2000 code points; the database
  enforces the same limits with `CHECK` constraints.
- **IDs** are hyphenated UUIDv7, accepted in any letter case.
- **Concurrency**: cards returned by GET and list include an integer `version`.
  GET/HEAD of a card, POST (201), and PUT (204) return a strong `ETag`, such as
  `"3"`, derived from that version. PUT and DELETE require `If-Match` with
  exactly one strong quoted positive integer. Missing or malformed values
  (including wildcards, lists and weak tags) return `428 precondition_required`.
  Stale versions return `412 precondition_failed`; unknown cards return 404
  before version mismatch. Requests check path ID, If-Match, binding,
  sanitization, validation, then storage. Each successful update increments
  the version atomically; clients must reload after a conflict.
- **Pagination**: `limit` (1–100, default 20) and `cursor` (the previous
  page's `next_cursor`, an opaque token to pass unchanged). `next_cursor` is
  `null` on the last page. Invalid tokens report `invalid_cursor`. Malformed
  or overflowing limits return `validation_error` with `invalid_integer`; integer limits outside 1–100
  return `validation_error` with `out_of_range`.
- **Request IDs**: every response carries `X-Request-Id`. The first client-supplied
  value is reused only if it contains 1–128 ASCII letters, digits, `.`, `_` or
  `-`. Missing, empty or invalid values are replaced with a random base32 ID,
  without rejecting the request. The selected ID is attached to every log
  record for that request.
- **Errors** share one JSON shape. Errors from shared middleware, such as
  oversized bodies and recovered panics, use it on every path, client-app
  paths included; the client app's own errors are plain text. `errors` is
  present only for validation failures in body fields, path parameters or
  query parameters:

  ```json
  {
    "code": "validation_error",
    "errors": [{ "field": "title", "code": "max_length" }]
  }
  ```

  | Code | Status | Meaning |
  | --- | --- | --- |
  | `bind_error` | 400 | Body could not be decoded |
  | `validation_error` | 400 | A body field, path parameter or query parameter failed validation |
  | `precondition_required` | 428 | Missing or malformed If-Match |
  | `precondition_failed` | 412 | Stale resource version |
  | `not_found` | 404 | Unknown card or unknown `/api` path |
  | `method_not_allowed` | 405 | Unsupported method, with an `Allow` header |
  | `payload_too_large` | 413 | Body over 1 MiB |
  | `unsupported_media_type` | 415 | Body is not `application/json` |
  | `unexpected_error` | 500 | Server-side failure; details are only logged |

  Field error codes: `required`, `max_length`, `untrimmed`, `not_normalized`,
  `invalid_integer`, `out_of_range`, `invalid_uuid7` (invalid path ID),
  `invalid_cursor` (invalid pagination token).

### Probes

`internal/infra/health` owns the probes surface (`health.Probes`) and the
shared `health.State`. The composition root mounts the probes and passes the
same state's `MarkStopping` to `server.Run` as its `OnDrain` hook, which runs
when shutdown begins.

`GET /livez` (and HEAD) returns 200 whenever the process can answer HTTP. It
checks no dependencies, including the database. Use it for liveness checks.
`GET /readyz` (and HEAD) returns 200 only when a database ping succeeds within
one second and the instance is not shutting down; otherwise it returns 503.
Use readiness to decide whether to send traffic to an instance.

Both paths live outside `/api` and require no authentication. Probe handlers
send `Cache-Control: no-store` and `X-Request-Id`. GET bodies are
`{"status":"ok"}` or `{"status":"unavailable"}`; HEAD sends no body.
Unsupported methods receive 405 with the shared JSON error body
`{"code":"method_not_allowed"}` and `Allow: GET, HEAD`.

The global 1 MiB body limit also applies to both paths. Oversized declared
bodies return JSON `413 payload_too_large` before the probe handler runs;
HEAD sends no body.

On SIGINT or SIGTERM, readiness becomes unavailable immediately. HTTP keeps
serving during `APP_SHUTDOWN_DRAIN_DELAY`, allowing load balancers to remove
the instance, then graceful shutdown begins with `APP_SHUTDOWN_TIMEOUT`.
The drain delay defaults to `0s`; deployments set it to match their routing
propagation time. A second signal terminates immediately during draining or
shutdown.

For a Docker Compose image containing `curl`, a readiness healthcheck can be:

```yaml
services:
  app:
    environment:
      APP_PORT: "8080"
      APP_SHUTDOWN_DRAIN_DELAY: "5s"
    stop_grace_period: 25s # Allow the drain delay plus the shutdown timeout.
    healthcheck:
      test: ["CMD", "curl", "--fail", "--silent", "--max-time", "2", "http://localhost:8080/readyz"]
      interval: 5s
      timeout: 3s
      retries: 3
```

### Configuration

The server reads its configuration from environment variables at startup and
reports every missing or invalid variable at once. The devcontainer sets the
required ones.

| Variable | Default | Description |
| --- | --- | --- |
| `DB_CONNECTION` | **required** | PostgreSQL URL (`postgres://` or `postgresql://`) |
| `APP_PORT` | **required** | Decimal HTTP port, 1–65535 |
| `DB_MAX_OPEN_CONNS` | `10` | Connection pool size |
| `DB_MAX_IDLE_CONNS` | `5` | Idle connections kept in the pool |
| `DB_CONN_MAX_LIFETIME` | `30m` | Maximum connection lifetime |
| `DB_CONN_MAX_IDLE_TIME` | `10m` | Maximum connection idle time |
| `APP_READ_TIMEOUT` | `5s` | HTTP read timeout |
| `APP_WRITE_TIMEOUT` | `10s` | HTTP write timeout |
| `APP_IDLE_TIMEOUT` | `90s` | HTTP keep-alive idle timeout |
| `APP_SHUTDOWN_TIMEOUT` | `15s` | Grace period for in-flight requests after draining on SIGINT/SIGTERM |
| `APP_SHUTDOWN_DRAIN_DELAY` | `0s` | Wait after marking the instance unready, before graceful shutdown |
| `APP_API_DOCS` | `false` | Serve the API reference at `/docs` (`make dev` sets `true`) |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn` or `error` |
| `LOG_FORMAT` | `json` | `json` or `text` |
| `DB_TEST_CONNECTION` | — | Test-only: server and role used by integration tests (needs `CREATEDB`) |

Durations use Go's `time.ParseDuration` syntax. The connection string is
logged at startup with its password redacted.

### Getting started

The repository ships a devcontainer (`.devcontainer/`) with Go, Node, the Go
tooling (Air, Delve, goose, golangci-lint) and two PostgreSQL 18 instances:

| Service | Host port | Purpose |
| --- | --- | --- |
| `db` | `5432` | Development database (persistent volume) |
| `db_test` | `5433` | Test server (tmpfs, fsync off, for speed) |

Open the repository in the devcontainer, then:

```sh
make migrate-up   # create the schema (the server does not migrate on startup)
make dev          # Go backend with Air live reload + Vite dev server
```

| URL | What |
| --- | --- |
| http://localhost:5173 | Client app via Vite (proxies `/api` and `/docs` to the backend) |
| http://localhost:8080 | Backend directly: `/api/...`, `/docs`, and embedded client assets |

On a fresh checkout, `make dev` embeds a placeholder page in the backend; use
port 5173 for the client app. To serve a real embedded client build on port
8080, run `make build-frontend` and restart `make dev`.

Run `make` or `make help` to list every target.

Air, Delve, goose, stringer and govulncheck are tracked as tools in the separate
`backend/tools/go.mod` module, with checksums in `backend/tools/go.sum`. This
keeps tool dependencies separate from the app's dependency graph. The devcontainer
installs those pinned versions for editor and PATH access. Make targets use
`go -C backend tool -modfile=tools/go.mod` to select them while running from
`backend`. From that directory, run `go tool -modfile=tools/go.mod <tool>`, where
`<tool>` is `air`, `dlv`, `goose`, `stringer` or `govulncheck`.

To update a tool, run `go -C backend/tools get -tool <package>@<version>`, then
`go -C backend/tools mod tidy`, and commit both tool module files. Keep the goose
CLI in `backend/tools/go.mod` and library in `backend/go.mod` on the same version;
when updating goose, also run `go -C backend get github.com/pressly/goose/v3@<version>`
and `go -C backend mod tidy`, and commit both app module files.

Each tool version has one source, which the devcontainer and CI both read:

| Tool | Source | Kept in sync by |
| --- | --- | --- |
| Go | `go` line in `backend/go.mod` | `make versions-check` fails when the devcontainer's `golang:` image tag or `backend/tools/go.mod` disagrees |
| golangci-lint | `GOLANGCI_LINT_VERSION` in the `Makefile` | `make install-golangci-lint` installs it (devcontainer and CI); `make versions-check` fails when the installed binary differs |
| Node | `engines.node` (a major version, `26.x`) in `frontend/package.json` | CI's `setup-node` reads it; `make versions-check` fails when the devcontainer's node feature or the installed `node` has another major version |
| oxfmt | Exact version in `devDependencies` of `frontend/package.json`, locked in `frontend/package-lock.json` | `make frontend-deps` installs it (CI), as does the devcontainer; Make targets and the editor run that installed copy |

To upgrade Go, change all three places in one commit. To upgrade the linter,
change `GOLANGCI_LINT_VERSION` and run `make install-golangci-lint`. To upgrade
Node, change `engines.node` and the devcontainer's node feature in one commit,
then rebuild the devcontainer. To upgrade oxfmt, which can change formatting,
change its pin, run `npm install` in `frontend/` and `make frontend-fmt`, and
commit the reformat on its own.

The API type generator (`openapi-typescript`) needs TypeScript 5's JavaScript
API, while the client app uses TypeScript 7, so it lives in its own package,
`frontend/tools/`, with exact pins and its own lockfile
([ADR 0031](docs/adr/0031-generated-api-types-and-typed-fetch-client.md)).
`make frontend-deps` installs the locked dependencies of both packages.

### Running without the backend

```sh
make dev-mock     # Vite dev server only; a fake backend answers /api in the browser
```

Open http://localhost:5173. [MSW](https://mswjs.io) intercepts the client
app's API requests and answers them from in-memory fakes in
`frontend/src/api/<service>/fake/`, so no Go server, database or migrations
are needed. The fake implements only what the client app's flows depend on:
state across requests, versions with `ETag` and `If-Match` (428 without it,
404 before 412), malformed IDs, opaque cursors and minimal validation
(trimmed, required, maximum length, page size). It doesn't reproduce the
backend's input parsing
([ADR 0032](docs/adr/0032-stateful-fake-backend-with-msw.md)). An API request
the fake has no handler for fails as a network error, with the request named
in the console, instead of reaching a server. The mock mode doesn't proxy to
the backend, so the API reference at `/docs` isn't available there.

Query parameters on the URL the app loads with choose the data:

| Parameter | Effect |
| --- | --- |
| `scenario=default` | About eight cards with varied markdown (also when omitted) |
| `scenario=empty` | No cards |
| `scenario=many` | 150 cards, more than one page |
| `scenario=failing` | Every API request answers `500 unexpected_error` |
| `delay=<ms>` | Adds that many milliseconds to every API response, for example `?scenario=many&delay=2000` |

The fake's state lives in the page's memory: changes survive navigation
inside the app, and reloading the page starts over from the parameters in
the address bar. In-app links drop them, so a reload after navigating starts
the default scenario. Seeded cards get new IDs on every load, so a card's
URL, such as its editor, shows "doesn't exist" after a reload. Each tab
runs its own fake, so a change made in one tab is invisible to another. To
produce a `412`, open a card's editor, change the card from the browser
console, then save:

```js
const id = location.pathname.split('/').pop()
const card = await (await fetch(`/api/lcards/${id}`)).json()
await fetch(`/api/lcards/${id}`, {
  method: 'PUT',
  headers: { 'Content-Type': 'application/json', 'If-Match': `"${card.version}"` },
  body: JSON.stringify({ title: 'Changed elsewhere', description: card.description }),
})
```

Production builds contain neither MSW's worker nor the fake.

### GitHub CLI in the devcontainer

Agents open pull requests with `gh`, authenticated by `GH_TOKEN`, which the
devcontainer reads from your machine (`remoteEnv` in `devcontainer.json`).
Out-of-scope findings become issues from the
[Follow-up template](.github/ISSUE_TEMPLATE/follow-up.yml) and are listed
under "Follow-ups" in the pull request instead of being fixed there (see
`AGENTS.md`, Issues). A pull request that fixes an issue says `Fixes #N` in its
description, and the issue closes when the maintainer merges it.

1. Create a fine-grained token limited to this repository, with
   **Pull requests: Read and write**, **Issues: Read and write** and
   **Contents: Read-only**. The read-only Contents permission is deliberate:
   the token can open pull requests and issues but cannot push or merge.
2. Save it to `~/.config/ludustudii/gh_token` (`chmod 600`) and export it from
   `~/.profile`:

   ```sh
   if [ -r "$HOME/.config/ludustudii/gh_token" ]; then
     export GH_TOKEN="$(cat "$HOME/.config/ludustudii/gh_token")"
   fi
   ```

3. Log out and back in, then rebuild or reopen the container.
   `gh auth status` inside the container should report the token.

Without `GH_TOKEN`, everything else works; agents just can't open pull
requests or issues.

### Testing

Unit tests use `<name>_test.go`; integration tests use
`<name>_integration_test.go`. Service API tests keep `api_test.go` as the
exception. Filenames identify the scope; retain the `unit` and `integration`
build tags to select which suite runs. `make test-tags-check` (part of
`make check`) fails when a test file's name and build tag disagree.

Tests are split by build tag:

| Command | Tag | Scope |
| --- | --- | --- |
| `make test-unit` | `unit` | Handlers, validation, kit, spec, fuzz contracts, with `-race`. No database. |
| `make test-integration` | `integration` | Stores and API tests against real PostgreSQL, with `-race` |
| `make test` | both | Everything |
| `make coverage` | `unit,integration,apidocs` | All backend tests with `-race`; writes `backend/coverage/coverage.out` and `backend/coverage/coverage.html`. Requires `DB_TEST_CONNECTION`. |

Both test targets accept `PKG` (default `./...`, relative to `backend`) and
`RUN` (a Go test name regex, default all tests). They use `-race`, `-count=1` and
`-shuffle=on` to detect races and dependencies on test order.

```sh
make test-integration PKG=./internal/services/lcards/... RUN=TestCreate
make test-unit PKG=./internal/services/lcards/create RUN='Test.*'
```

The extra unit-test run with the `apidocs` tag runs only when `PKG` includes
that package, and uses the same `RUN` filter.

To view the coverage report from the devcontainer, run this from the repository
root:

```sh
python3 -m http.server 8000 --directory backend/coverage
```

Forward port 8000 in VS Code's **Ports** tab, then open the forwarded URL with
`/coverage.html`. Stop the server with Ctrl+C when finished.

The testing strategy is deliberate:

- **Handler tests** (`handler_test.go`, unit) replace each step — bind, validate, store — through
  function fields and interfaces, so every step is tested in isolation.
- **Store tests** (`store_integration_test.go`, integration) run real SQL against a real database; stores
  have no unit tests or mocks.
- **API tests** (`api_test.go`, integration) drive the full router over HTTP with a real
  client and database, covering routing, middleware and error handling.
- **Contract tests** fuzz the sanitizer against the validators, so sanitized
  input always passes the format checks.

`testkit` makes integration tests isolated and parallel-safe: on first use it
creates a template database on `DB_TEST_CONNECTION` and migrates it, then gives
every test its own `CREATE DATABASE ... TEMPLATE` clone, dropped when the test
ends. Packages with integration tests opt in from `TestMain`:

```go
func TestMain(m *testing.M) {
	os.Exit(testkit.Run(m))
}
```

Every response received through `testkit.Do` is validated against the OpenAPI
spec (status, headers and body schema), so the implementation and the spec
can't drift apart unnoticed.

### API spec and reference

The spec is split across `backend/apispec/openapi.yml`, `paths/` and
`components/`. The reference page serves a single bundled copy at
`backend/internal/infra/apidocs/dist/openapi.json`, which is committed.

- `make spec-bundle` regenerates the bundle when a spec file changed. Air runs
  it on every rebuild during `make dev`.
- A unit test fails if the committed bundle is stale.
- `make api-types` generates the client app's types,
  `frontend/src/api/schema.gen.ts`, from the bundle. The file is committed;
  `make api-types-check` fails when it is stale. After a spec change, run
  `make api-types` and commit the bundle and the types together. If the
  client app calls the endpoint, update its fake as well
  ([Running without the backend](#running-without-the-backend)).

The reference UI is the Scalar standalone script, taken from
`frontend/node_modules`, gzipped and embedded only when building with the
`apidocs` tag. It is fully self-hosted (no external fonts or AI agent). If the
tag is set but the script is missing, the server logs a warning and starts
without `/docs`.

### Logs

`make dev` appends the backend's JSON logs to `backend/tmp/app.log` (override
with `LOG_FILE=...`). These targets query it with `jq`:

| Command | Purpose |
| --- | --- |
| `make logs` | Follow and pretty-print the log |
| `make logs-errors` | `ERROR` and `WARN` records |
| `make logs-req ID=<request id>` | Every record for one request |
| `make logs-slow MS=500` | Requests slower than `MS` ms (default 200) |
| `make logs-stats` | Request counts by status, method and route |

Each request produces one `request` record with method, route, path, status
and latency, logged at `ERROR` for 5xx, `WARN` for 4xx and `INFO` otherwise.
The quiet probe paths `/livez` and `/readyz` log their summaries at `DEBUG`
regardless of status. Readiness logs state transitions once: `WARN` with the
reason when becoming unavailable, `INFO` on recovery, and `INFO` when stopping
starts. Repeated failed probes do not repeat the warning.

### Building

```sh
make build              # frontend bundle + static Go binary → backend/bin/ludustudii
make build API_DOCS=1   # also embed the API reference (dev, test and staging builds)
make clean              # remove build outputs and embedded assets
```

The binary is built with `CGO_ENABLED=0` and embeds the client app and the
OpenAPI spec. `make build-backend` refuses to build without a real frontend
bundle. A binary built without `API_DOCS=1` fails to start if
`APP_API_DOCS=true`, since that is a deployment mistake.

### Linting

Run these commands from the repository root. The devcontainer and CI install the
pinned standalone golangci-lint binary with `make install-golangci-lint`; lint
tooling is kept out of `go.mod`.

| Command | Purpose |
| --- | --- |
| `make check` | Run all required gates in order; agents and CI use this. Requires `DB_TEST_CONNECTION`. |
| `make versions-check` | Fail if the devcontainer or tool module Go version, or the installed golangci-lint, differs from its single source. |
| `make install-golangci-lint` | Install golangci-lint at `GOLANGCI_LINT_VERSION`. |
| `make lint` | Check the backend and tagged tests. |
| `make lint-fix` | Apply available automatic lint fixes. |
| `make fmt` | Format Go source with gofumpt and goimports. |
| `make fmt-check` | Fail if any Go file needs formatting. |
| `make test-tags-check` | Fail if a backend test file's name and build tag disagree. |
| `make pr-title-check` | Fail if `PR_TITLE` breaks the pull request title format (`type: summary`, at most 64 characters). |
| `make pr-title-check-test` | Run `pr-title-check` against a table of valid and invalid titles and fail on an unexpected result. |
| `make tidy-check` | Fail if the app or tool module's `go.mod` or `go.sum` needs tidying. |
| `make generate-check` | Regenerate backend files and fail if generation changes tracked backend files. |
| `make api-types-check` | Regenerate the client app's API types and fail if they differ from the committed file. |
| `make frontend-typecheck` | Type-check the client app. |
| `make frontend-fmt` | Format the client app with oxfmt. |
| `make frontend-fmt-check` | Fail if any file of the client app needs formatting. |
| `make frontend-deps` | Install the locked dependencies of `frontend/` and `frontend/tools/`. |
| `make lint-verify` | Validate `backend/.golangci.yml`. |
| `make vuln` | Check backend packages for known vulnerabilities with govulncheck. |

`make check` runs `versions-check`, `fmt-check`, `frontend-fmt-check`,
`test-tags-check`, `pr-title-check-test`, `lint`, `tidy-check`,
`generate-check`, `api-types-check`, `frontend-typecheck`, `test-unit` and
`test-integration` sequentially, stopping at the first failure. It needs the
frontend dependencies (`make frontend-deps`).

`make generate-check` includes the committed OpenAPI bundle. It leaves regenerated
files on disk for review and ignores pre-existing edits that generation leaves unchanged.

Lint uses the `unit,integration,apidocs` build tags so tests are included.
The alternate `script_none.go` build is intentionally omitted from linting.

oxfmt formats the client app with its defaults
([ADR 0033](docs/adr/0033-oxlint-and-oxfmt-for-the-client-app.md)).
`frontend/.oxfmtrc.json` sets no style options; it only ignores the generated
files (`src/api/schema.gen.ts`, `src/routeTree.gen.ts`) and the lockfiles. In
the devcontainer, the Oxc extension formats JavaScript, TypeScript and CSS
files on save.

`.git-blame-ignore-revs` lists formatting-only commits, so blame shows the
change before them. GitHub's blame view uses it automatically; locally, run
`git config blame.ignoreRevsFile .git-blame-ignore-revs` once per clone. Every
later formatting-only commit (such as enabling import or Tailwind class
sorting, #18 and #19) adds its hash to the file.

#### Exclusion policy

Use `backend/.golangci.yml` for shared rules: generated files and bundled assets,
standard exclusion presets, test fixtures, and package boundaries.

For a one-off exception, place `//nolint:<linter> // <reason>` beside the code
with the smallest practical scope. Name the linter and explain the deliberate
behavior or false positive; prefer a real fix when the finding identifies a bug.
For gosec, use `// #nosec Gxxx -- <reason>` to suppress only the relevant check.

### CI

GitHub Actions runs the same gate as a developer
([ADR 0028](docs/adr/0028-ci-reuses-the-devcontainer-test-database.md)):

| Workflow | When | What |
| --- | --- | --- |
| [`ci.yml`](.github/workflows/ci.yml) | Every push to `main` and every pull request; a newer push to a pull request cancels its older run, while runs on `main` always finish | `make check` |
| [`pr-title.yml`](.github/workflows/pr-title.yml) | Every pull request when it is opened, reopened, pushed to or edited, so fixing the title re-runs it | `make pr-title-check` with the pull request title, which must be `type: summary` within 64 characters |
| [`vuln.yml`](.github/workflows/vuln.yml) | Daily at 03:17 UTC, or on demand | `make vuln` |

The CI job installs Go from `backend/go.mod`, Node from `engines.node` in
`frontend/package.json`, golangci-lint with `make install-golangci-lint`, and
the frontend dependencies with `make frontend-deps`. It starts only `db_test`
from `.devcontainer/docker-compose.yml` (`docker compose up -d --wait db_test`)
and points `DB_TEST_CONNECTION` at `localhost:5433`.

A failing `ci.yml` run means the change isn't done. To run the vulnerability
scan by hand, open **Actions → Vulnerability scan → Run workflow**, or run
`gh workflow run vuln.yml`.
